0. 全景图：MCU 开发的知识地图

MCU（Microcontroller Unit，微控制器）的本质是把 CPU、存储器（Flash / SRAM）和常用外设（串口、定时器、ADC 等）集成在一片芯片上的单芯片计算机。它和 PC 最大的区别不是性能低，而是「程序直接跑在裸金属上」：没有操作系统帮你管理内存和外设时（裸机开发），每一字节的去向、每一个中断的时序，都是工程师自己的责任。整个 MCU 开发的知识体系因此分成四层：

 应用层     状态机 / 任务调度 / 协议解析(MAVLink, Modbus) / 日志 / 故障管理
 ─────────────────────────────────────────────────────────────
 中间件     FreeRTOS(实时操作系统) / FatFs(文件系统) / LwIP(网络) / USB 协议栈
 ─────────────────────────────────────────────────────────────
 驱动层     HAL(意法半导体的通用硬件抽象库) / LL(轻量寄存器封装) / 直接写寄存器
 ─────────────────────────────────────────────────────────────
 硬件层     Cortex-M 内核 + 时钟树(RCC) + 中断控制器(NVIC)
            + 外设: UART / SPI / I2C / CAN / ADC / 定时器 / DMA
            + 存储: Flash(放代码) / SRAM(放变量) / 备份域

本手册的章节正好沿着这个分层自底向上：先选芯片和搭工程（硬件层 + 驱动层入口），再逐个吃透外设驱动（驱动层），最后管内存、查故障（支撑系统稳定运行的横切能力）。

0.2 MCU 与它的亲戚

选型第一步是确认「我到底需要哪类芯片」。MCU 与 MPU（应用处理器）、DSP、无线 SoC 的边界经常被混淆，下表给出判据：

类别 代表 程序与系统 强项 弱项 典型用途
MCU（本手册对象） STM32、GD32、CH32、RA、AURIX 裸机或 RTOS，代码在片内 Flash 就地执行 微秒级实时性、低功耗、上电即跑、外设丰富 算力有限（通常不超过数千 CoreMark），不适合跑通用操作系统 电机控制、飞控、传感器节点、车身控制
MPU（应用处理器） i.MX8、RK3568、树莓派芯片 Linux / Android，代码在外挂 DDR / eMMC 千兆级算力、通用操作系统生态 启动慢（秒级）、功耗高、实时性弱（毫秒抖动） 视觉处理、HMI、网关
DSP（数字信号处理器） TI C2000、C6000 裸机 / RTOS，乘加与滤波指令专用化 数字电源、电机 FOC 中的高频滤波与变换 通用外设与生态弱于主流 MCU 数字电源、逆变器
无线 SoC ESP32、Nordic nRF52 MCU 内核 + 射频收发器集成 无线连接开箱即用、社区生态（Arduino / ESP-IDF） 模拟外设（ADC）精度一般，硬实时不如 STM32 物联网终端、遥测链路
异构双芯系统 无人机算力板（实时 MCU + Linux SoC 分工） 两颗芯片各跑各的系统，经串口 / 网口互联 实时与算力兼得 两套工具链、联调复杂 无人机、机器人主控

判断口诀：需要微秒级确定响应、电池供电、单芯片解决 → MCU；需要跑 Linux、看视频、跑大模型 → MPU；两者都要 → 异构组合。

1. 芯片选型：参数逐项解读

选型的原则是「由需求倒推参数，而不是由参数追逐性能」：先列出接口清单（几个串口、要不要 CAN、ADC 几路），再估算算力与内存，最后用电气参数与商务因素收口。新手最常见的两个错误是「按主频选芯片」（主频只代表整数运算吞吐，不代表外设与实时性）和「预留过度」（为一个可能永远不做的功能多花一倍成本）。本章按参数重要性逐项展开。

1.1 内核与计算性能

内核决定「每兆赫兹能算多少」，主频决定「一共能算多快」，两者相乘才是真实算力。Cortex-M 家族的分级如下：

内核 流水线 DMIPS/MHz CoreMark/MHz FPU DSP 指令 TrustZone 典型芯片 定位
Cortex-M0 3 级 约 0.9 约 2.3 无 无 无 STM32F0 替换 8 位机的 32 位入门
Cortex-M0+ 2 级 约 0.95 约 2.4 无 无 无 STM32G0、RP2040 超低功耗 / 超低成本
Cortex-M3 3 级 1.25 约 3.4 无 无 无 STM32F1、GD32F103 经典通用，无浮点
Cortex-M4 3 级 + 分支预测 1.25 约 3.4 单精度 有 无 STM32F4、G4 主力：算法 + 实时兼顾
Cortex-M7 6 级双发射 约 2.1 约 5.0 单精度（可配双精度） 有 无 STM32F7 / H7 高性能：大缓存、TCM
Cortex-M33 3 级 + 约 1.5 约 4.0 单精度可选 可选 有 STM32L5 / U5 / H5 带安全隔离的新一代中端
Cortex-M85 超标量 约 3.8 约 6.6 双精度 Helium 向量扩展 有 Renesas RA8 当前 MCU 顶级内核

DMIPS（Dhrystone MIPS）与 CoreMark 是两个业界基准分数，乘以主频即得总性能。例如 STM32F407（M4，168 MHz）：1.25 × 168 ≈ 210 DMIPS，3.4 × 168 ≈ 570 CoreMark；STM32H743（M7，480 MHz）约 1027 DMIPS、约 2400 CoreMark。不同厂家编译优化等级不同，实际有 10% 左右浮动。

算力估算的正确姿势是把最重的那一个实时任务算清楚，而不是笼统比分数。以飞控姿态环为例：1 kHz 中断内做一次四元数姿态解算 + 三轴 PID，乘加次数约 200 次（M4 的 DSP 指令单周期乘加），加传感器读取与滤波，单次约 5–10 μs，占 1 ms 周期的 1%——任何 M4 都绰绰有余；但若再加上卡尔曼滤波的 4×4 矩阵求逆（含除法），单次升到 50–100 μs，仍然安全；一旦出现「要跑 1024 点 FFT 频谱分析（约 1–2 ms）」这类需求，就必须确认 FPU 存在且采样 buffer 放对内存。结论：M0/M3 适合逻辑控制，凡是涉及浮点控制律、滤波、FFT 的应用，从 M4F 起步。

FPU 与编译选项的隐藏关联

硬件 FPU 只有配合正确的编译选项才生效。GCC 下 -mcpu=cortex-m4 -mfpu=fpv4-sp-d16 -mfloat-abi=hard 表示使用 F4 的单精度浮点单元并以硬浮点 ABI 传参；如果误用 -mfloat-abi=soft，所有浮点运算退化成软件模拟（慢 10–100 倍），主频再高也救不回来。Keil（MDK）同理，在 Target 对话框里确认「Floating Point Hardware」已选 Single Precision。另外注意：M4/M7（H7 系列）的 FPU 是单精度的，代码里的 double 字面量（如 3.14159 默认就是 double）会掉进软件浮点——写成 3.14159f 强制单精度是嵌入式 C 的关键习惯。

1.2 存储资源

存储决定「程序装不装得下、变量放不放得下、数据存不存得住」，选型时按三个维度核对：

维度 关键参数 解读与经验值
Flash 容量 代码 + 常量 + 文件系统占用 裸机逻辑程序典型 32–128 KB；带 RTOS + 网络协议栈 256 KB 起步；带字库 / 图标资源看资源大小。选型时留 30% 余量给迭代
Flash 寿命 擦写次数（1 万–10 万次） 参数掉电保存不能直接写 Flash——1 秒写一次，3 万次擦写不到一天就写穿；应写入 9.7 节的磨损均衡方案或外挂 EEPROM / FRAM
SRAM 容量 静态变量 + 栈 + 堆 + DMA 缓冲 估算方法：所有全局数组加起来 × 1.5（余量），再加 2–8 KB 栈。缓冲密集应用（如 CAN 报文队列、串口环形缓冲）单独列表核对。内存区域细节见第 9 章

另一个容易忽视的维度是内存结构：同样的 192 KB RAM，F407 是「128 KB 普通 SRAM + 64 KB CPU 专用 CCM」，H743 是「128 KB 全速 TCM + 864 KB 分域 SRAM + 可选缓存」——容量相同，带宽和可访问性完全不同（例如 F4 的 CCM 区 DMA 不可达，放串口缓冲就是死路）。这个问题复杂到值得单独一章，见第 9 章。

1.3 外设资源清单

外设清单是选型中最「硬」的约束——数量不够没有软件手段可救。逐项核对时关注的重点如下：

外设 选型关注点 常见的坑
UART 数量；是否有 FIFO（F4 无、F7/H7 有 16 字节）；最高波特率；流控引脚 数量按「每个设备一条」清点：GPS、数传、调试、RS485 各占一条，5 个设备就需要 5 个 UART
SPI 数量；最高速率（APB 时钟 ÷ 2）；是否支持 16 位帧；F7/H7 的 FIFO 深度 速率上限取决于所在总线：F407 的 SPI1 挂在 84 MHz 的 APB2 上限 42 Mbps，SPI2/3 挂在 42 MHz 的 APB1 上限只有 21 Mbps
I2C 数量；支持速率（100 k / 400 k / 1 MHz）；数字滤波能力 F1/F4 的旧版 I2C 外设时序 quirks 多（见 6.2 节），对外设密集的总线建议选 F7/G4/H7 的新版 IP
CAN 数量；经典 CAN 还是 CAN FD；过滤器组数量与深度 F4 的 bxCAN 只有经典 CAN；需要 CAN FD 必须选 G4（3 路）/H7/L5/U5 等带 FDCAN 的型号
ADC 位数（12/16 bit）；采样率；通道数；是否多 ADC 交替采样；注入通道 「12 bit」不等于「12 bit 有效」：实际有效位数（ENOB）通常少 1–2 bit，与布局和参考电压强相关
定时器 高级定时器（带死区互补 PWM，电机 / 电源必需）数量；32 位定时器数量 编码器接口模式需要两个通道正交解码，占用一个通用定时器的全部 4 个通道
USB FS（12 Mbps）/ HS（480 Mbps，F4 需外接 ULPI PHY）；设备 / 主机 / OTG 「有 USB」不等于「有高速」：HS 模式大多需要外挂 PHY 芯片，BOM 成本与布线难度陡增
SDMMC / Ethernet SDIO 4 线；以太网 MAC 是否带 PHY（多数不带，需外挂） 大容量数据记录（飞控日志）优先核对 SDMMC 是否存在，否则只能 SPI 卡，写入速率差一个量级
QSPI 是否支持内存映射执行代码（XIP） 大程序放外部 QSPI Flash 时，XIP 性能受限于 QSPI 带宽，热点函数应拷到片内 RAM 执行

1.4 电气参数与功耗

电气参数决定芯片「能不能在你的板子上活下来、省不省电」，以下项目逐条核对：

参数 典型值 注意事项
供电范围 2.0–3.6 V（主流）/ 1.71–3.6 V（H7） 主流 MCU 都是 3.3 V 供电；5 V 直连会损坏，5 V 系统需 LDO 降压
IO 电平与耐压 多数引脚 3.3 V；标「FT」的引脚 5 V 耐受 接 5 V 传感器输出时必须确认该脚是 FT（Five-volt Tolerant）脚，且 FT 脚不能配置为模拟 / 开漏上拉模式
IO 驱动能力 ±8 mA 保证，峰值 20–40 mA（视型号） 直接驱动 LED / 蜂鸣器可以，驱动继电器 / 电机必须加三极管或驱动芯片
运行功耗 约 0.1–0.3 mA/MHz（视工艺与频率） 168 MHz 全速运行约 30–40 mA；H7 480 MHz 可达 200 mA 以上
低功耗模式 Sleep（μs 级唤醒）/ Stop（μA 级）/ Standby（nA 级，唤醒即复位） 电池产品选型时逐档核对电流值：同级芯片 Stop 模式电流可能差 5–10 倍
备份域 RTC + 4 KB 备份 SRAM，VBAT 纽扣电池供电 断电保存标定参数 / 故障记录的硬件基础，见 9.6 节
复位与监控 POR / PDR（上下电复位）、BOR（欠压复位）、独立看门狗 IWDG 电源缓慢爬升场景必须使能 BOR，否则可能停在中间电压状态跑飞
温度等级 消费 0–85 ℃ / 工业 −40–85 ℃ / 车规 −40–125 ℃（AEC-Q100 Grade 1–3） 户外与车载必须工业级起步；同一内核不同温度等级差价明显

1.5 封装与硬件设计相关

封装影响的不只是焊接难度，还有信号完整性与散热。

封装 引脚间距 适用场景
SOIC / TSSOP 1.27 / 0.65 mm 小引脚数（8–28 脚）入门芯片，烙铁可焊
LQFP 0.5 / 0.8 mm 原型与小批量主力（F407VGT6 即 LQFP-100），热风枪或风枪返修可行
QFN / DFN 0.5 mm，底部带散热焊盘 量产省空间；底部焊盘需回流焊，手工返修困难

两个与选型直接相关的硬件问题：其一，时钟精度。内部 RC 振荡器（HSI）精度约 ±1%，对 UART 115200 波特率（要求总误差约小于 2%）勉强够用，但 CAN 总线（要求约 0.5% 以内）和 USB 必须用外部晶振（±10~±30 ppm）——选型时确认所用外设对时钟源的要求，别为省一个晶毁掉整条总线。其二，引脚复用冲突。MCU 每个引脚可复用为多种外设功能，但同一时刻只能一种；把外设需求列表逐脚映射时（CubeMX 会自动标红冲突），常见冲突点是大引脚数外设（SDMMC、8080 并口 LCD）与定时器通道抢占同组引脚。

认证资质 工业 IEC 61508（功能安全 SIL）、车规 ISO 26262（ASIL）、AEC-Q100 目标市场有强制认证要求时，认证芯片清单之外没有选择权

2.4 国产替代的注意事项

「兼容 STM32」的真实含义是寄存器与封装兼容，不保证模拟精度、时序细节与极限参数等效。已知的常见差异点：

差异点 典型表现 验证方法
Flash 等待周期 GD32 内置加速机制，同主频下取指等待少，循环基准测试比 ST 快——反之也可能暴露 ST 上没出现的时序敏感代码 跑同一段基准代码对比周期数（DWT 计数器，10.1 节）
5V 耐压（FT）引脚分布 GD32F103 等型号多数引脚不耐 5V，而对应 ST 引脚是 FT 脚——硬件直接替换可能损坏 IO 逐脚核对数据手册 Pin Definition 表
ADC 精度与噪声 实测 INL / DNL、温漂与原厂有差距，精密采样场景（称重、电量计）直接受影响 恒压源全通道扫描 + 温箱拉偏
内部 RC 精度 HSI 精度略差于 ST，无晶振走 UART 的设计风险升高 多台设备量产抽测波特率误差
外设行为细节 个别标志位时序、DMA 请求映射、USB 枚举细节有出入，HAL 库是各家自己维护的移植版 全接口自动化回归（串口全波特率收发、SPI 全模式、Flash 擦写循环、深度睡眠电流）

二供导入的正确姿势：软件按「同一套应用代码 + 各家 HAL」编译，硬件按「逐脚核对 + 抽样上电」验证，最终以一套自动化回归测试通过为准——这与测试台架上验证固件版本是同一套方法论。

3.2 CubeMX 配置五步法

以「168 MHz 主频 + SWD 调试 + USART1 打印 + LED」为目标，CubeMX 操作顺序如下（顺序本身有讲究，最后才摆功能引脚）：

  1. 选型：New Project → MCU/MPU Selector → 搜 STM32F407VGT6 → Start Project。
  2. 调试口：左侧 System Core → SYS → Debug 选 Serial Wire。不选的后果：PA13/PA14 被释放为普通 GPIO，烧录一次程序后 SWD 被复用占用，调试器再也连不上（只能 connect under reset 抢救）。这是新手第一大坑。
  3. 时钟源：System Core → RCC → HSE（外部高速晶振）选 Crystal/Ceramic Resonator。前面 1.5 节说过，UART/USB/ADC 精度场景必须外部晶振。
  4. 时钟树：Clock Configuration 页，输入 HSE = 8 MHz，按下面路径逐级设置（CubeMX 会自动解算，也可手输回车确认）：
 HSE 8 MHz
   │  /M = 4
   ▼
 2 MHz ──(PLL 锁相环 ×N = 168)──► 336 MHz VCO
                                     │ /P = 2
                                     ▼
                          SYSCLK = 168 MHz（系统主频）
                            │ /AHB = 1  → HCLK  = 168 MHz（CPU/ DMA / SRAM）
                            │ /APB1 = 4 → APB1  =  42 MHz（低速外设: UART2~5, SPI2/3, I2C, CAN1/2, TIM2~7）
                            │ /APB2 = 2 → APB2  =  84 MHz（高速外设: UART1, SPI1, ADC, TIM1/8~11）
   注: 挂在 APB 上的定时器时钟自动 ×2（APB 分频大于 1 时）, 如 TIM2 时钟 = 84 MHz

时钟树是 STM32 的「总闸」：所有外设的实际速率（波特率、SPI 分频、ADC 采样率）都从这里的三个总线时钟派生，后面每一章算参数时都会回到这组数字（168 / 42 / 84 MHz）。

  1. 外设与引脚：本例勾选 USART1（Mode: Asynchronous，115200），PB0 设为 GPIO_Output（LED）；然后 Project Manager 页设工程名与 IDE，Code Generator 页勾选「Generate peripheral initialization as a pair of '.c/.h' files per peripheral」（外设初始化分文件，工程大后必要）与「Copy only the necessary library files」（只拷用到的库）。GENERATE CODE。

3.3 生成代码的结构与 USER CODE 机制

├─ Core/
│  ├─ Src/
│  │  ├─ main.c              ← main() 与外设初始化入口
│  │  ├─ gpio.c              ← GPIO 初始化（按外设分文件的产物）
│  │  ├─ usart.c             ← USART1 初始化

│  │  ├─ stm32f4xx_it.c      ← 所有中断服务函数入口

│  │  └─ system_stm32f4xx.c  ← SystemInit(): 时钟相关系统初始化

有两个文件值得提前理解。其一是启动文件 startup_stm32f407xx.s：复位后 CPU 从这里执行——先把 .data 段（有初值的全局变量）从 Flash 复制到 RAM，再把 .bss 段（无初值全局变量）清零，然后跳进 main()。段的概念在第 9 章展开。其二是 USER CODE 区：生成的 main.c 里到处是这样的注释对：

/* USER CODE BEGIN 2 */
  用户代码只能写在这对注释之间
/* USER CODE END 2 */

CubeMX 重新生成代码时只改注释对之外的内容，注释对之内的用户代码原样保留。把代码写在注释对之外等于写在沙子上，下次生成必被覆盖——这是 CubeMX 工作流的第一纪律。

3.4 HAL 库的两种打开方式与点灯

HAL（Hardware Abstraction Layer）是 ST 的官方抽象库，把「配置寄存器」封装成「结构体 + API」；它的轻量替代是 LL（Low-Layer）库，直接对应寄存器操作，无运行时开销。两者取舍：

维度 HAL LL 寄存器直写
代码效率 较低（参数检查、状态机开销） 高（内联宏） 最高
开发速度 最快，CubeMX 深度集成 较快，CubeMX 可生成 LL 代码 最慢，需通读参考手册
可移植性 同系列内换型号几乎零成本 同系列内良好 换型号需逐寄存器核对
适用 应用层、原型、多数商业项目 时序敏感的内外层（中断里翻转 IO） 极致性能点（如 1 kHz 控制环内层）

典型策略：外设初始化交给 CubeMX 生成（HAL 或 LL），性能关键路径用 LL 或寄存器改写。点灯示例（CubeMX 已生成 MX_GPIO_Init()，用户代码写在 USER CODE 区）：

int main(void)
{
  HAL_Init();                 // 1) HAL 库初始化: 配 SysTick 1ms 时基、NVIC 优先级分组
  SystemClock_Config();       // 2) 时钟树配置(上面 168MHz 的那条路径), CubeMX 生成
  MX_GPIO_Init();             // 3) 外设初始化, CubeMX 生成, 顺序 = CubeMX 里的勾选顺序
  MX_USART1_UART_Init();

  /* USER CODE BEGIN WHILE */
  while (1)
  {
    HAL_GPIO_TogglePin(GPIOB, GPIO_PIN_0);   // 翻转 PB0
    HAL_Delay(500);                          // 阻塞延时 500ms, 基于 SysTick 中断计 1ms 次数
  }
  /* USER CODE END WHILE */
}

LED 闪烁起来了，工程就「通了」：编译链、烧录器、最小硬件全部验证完毕。之后每加一个外设都应遵循同样的节奏——先让最小验证程序跑通，再逐步加功能。

3.5 printf 重定向与 HAL 库的底层机制

嵌入式没有控制台，printf 需要重定向到串口。GCC（CubeIDE / VSCode）重定向 _write，Keil 重定向 fputc：

/* GCC(CubeIDE): 重定向 _write 到 USART1 */
#include <unistd.h>
int _write(int fd, char *ptr, int len)
{

3.6 HAL 库的三个底层机制

读懂这三个机制，HAL 的所有外设章节就都顺了：

（1）句柄（Handle）结构体

每个外设实例对应一个句柄：UART_HandleTypeDef huart1、SPI_HandleTypeDef hspi1、CAN_HandleTypeDef hcan1。句柄里装着配置参数（波特率、数据位……）、运行状态（HAL_UART_STATE_READY / BUSY）和缓冲区指针。HAL API 的第一个参数永远是句柄——HAL 是有状态的库，状态机错误（如 BUSY 状态下再次调用）是常见故障源。

（2）MSP 回调：初始化的两段式

调用 HAL_UART_Init(&huart1) 时，HAL 会自动回调 HAL_UART_MspInit()（MCU Support Package，MCU 支持包），后者负责「这个外设挂在哪个引脚、开哪个时钟、配哪个中断」——这部分代码 CubeMX 生成在 stm32f4xx_hal_msp.c。于是初始化被拆成两层：Init 配置「协议参数」（与板子无关），MSP 配置「物理连接」（与板子强相关）。改板子只动 MSP，换波特率只动 Init，这就是两段式的意义。

（3）回调（Callback）：中断的面向对象化

中断服务函数（stm32f4xx_it.c 里的 USART1_IRQHandler 等）先调用 HAL_UART_IRQHandler(&huart1)，HAL 判断事件类型后再回调弱定义函数：HAL_UART_RxCpltCallback()（收到指定字节数）、HAL_UART_TxCpltCallback()（发送完成）、HAL_UART_ErrorCallback()（错误）。用户的业务逻辑写在这些弱函数的重写版里。注意：这些回调不分外设实例——函数参数里给的是句柄指针，用 if (huart == &huart1) 区分是哪个串口触发的事件。

3.7 工程实践四要点

  1. 错误处理不能裸奔：CubeMX 生成的每个 Init 失败都会进 Error_Handler()（默认死循环）。量产代码至少应记录错误码并尝试降级运行，死循环等于现场黑屏。
  2. HAL_Delay 的适用边界：HAL_Delay 依赖 SysTick 中断计数，在中断服务函数里调用会死锁（中断里 SysTick 进不来，计数值永远不动）。中断内延时用 DWT 周期计数器（10.1 节）或定时器。另外 FreeRTOS 工程里 vTaskDelay（让出 CPU）才是正解，HAL_Delay 只配做纳秒级粗延时。
  3. NVIC 优先级分组一次定死：HAL_Init() 里已设 NVIC_PRIORITYGROUP_4（4 位全做抢占优先级，0 位子优先级）。Cortex-M 推荐只用抢占、不用子优先级；上 FreeRTOS 后还要遵守 configMAX_SYSCALL_INTERRUPT_PRIORITY（低于此优先级的中断不能调用 FreeRTOS 的 FromISR API），优先级规划应在建工程时画一张表。
  4. 时基源切换：FreeRTOS 默认占用 SysTick，CubeMX 会提示把 HAL 时基改为另一个基本定时器（如 TIM6）。不改的后果是两套系统抢同一个 SysTick，延时全乱。CubeMX 在 FreeRTOS 使能时会自动处理，手工建工程时容易漏。

4. UART：异步串口与不定长接收

UART（通用异步收发器）是嵌入式调试与低速通信的第一通道，看似简单，但「收不定长的报文」是所有新手都会撞上的第一道真正的设计题。本章从帧格式与波特率误差讲起，给出三级递进的接收方案（轮询 → 中断环形缓冲 → DMA 空闲检测），后两者是面试与实战的必备题。

4.1 协议原理：帧格式与波特率

UART 是异步协议：没有时钟线，收发双方靠事先约定的波特率各自计时。一帧数据的结构：

 空闲(高电平)

4.2 STM32 USART 的波特率发生器

波特率由总线时钟分频得到：波特率 = fCK / (16 × USARTDIV)（16 倍过采样模式），USARTDIV 是 12 位整数 + 4 位小数的 BRR 寄存器值。算一遍真实误差，理解「哪些波特率是安全的」：

例: USART2 挂在 APB1 (42 MHz), 目标 115200
  USARTDIV = 42 MHz / (16 × 115200) = 22.786
  BRR     = 整数 22 | 小数 0.786 × 16 ≈ 12.6 → 取 13 (0xD)
  实际值   = 22 + 13/16 = 22.8125
  实际波特率 = 42e6 / (16 × 22.8125) = 115115.2
  误差   = (115115.2 − 115200) / 115200 = −0.074%   ✔ 安全

例: 同一时钟, 目标 921600
  USARTDIV = 42e6 / (16 × 921600) = 2.849 → 取 2.875
  实际波特率 = 913043, 误差 = −0.93%              ⚠ 单边已近 1% 安全线
  对端若也偏 +0.9%, 总误差逼近 2%, 高温漂移下偶发误码

工程结论：波特率越高，时钟源质量越重要。使用内部 HSI（±1%）时 115200 勉强可用，921600 以上必须外部晶振；CubeMX 会自动算 BRR 并显示误差百分比，配置页直接可查。另外 F4 的 USART1 挂在 84 MHz 的 APB2 上，同样的波特率误差比 APB1 上的串口更小——高速串口优先用挂在高速总线的 USART1/6。

4.4 中断 + 环形缓冲接收：完整驱动

设计要点有三个。其一，中断里只做一件事——把字节塞进环形缓冲，绝不解析协议（中断要短）。其二，环形缓冲用「单生产者-单消费者」无锁写法：head 只有中断改，tail 只有主循环改，两者都是 volatile 单向推进，天然线程安全，不需要关中断保护。其三，缓冲区大小取 2 的幂，用按位与代替取模求余。

/* uart_ring.c —— 中断+环形缓冲接收驱动 (F407, USART2, 寄存器版) */
#define UART_RB_SIZE 256          /* 必须是 2 的幂 */

typedef struct {
    volatile uint16_t head;        /* 写指针: 只有中断服务程序修改 */
    volatile uint16_t tail;        /* 读指针: 只有主循环(或消费者任务)修改 */
    uint8_t buf[UART_RB_SIZE];
} ringbuf_t;

static ringbuf_t uart2_rb;

/* 中断服务函数: stm32f4xx_it.c 里由向量表调用 */
void USART2_IRQHandler(void)
{
    if (USART2->SR & USART_SR_RXNE) {              /* 收到一个字节 */
        uint8_t byte = (uint8_t)USART2->DR;         /* 读 DR, 同时自动清 RXNE 标志 */
        uint16_t next = (uart2_rb.head + 1) & (UART_RB_SIZE - 1);
        if (next != uart2_rb.tail) {                /* 满: 留一个空位用于区分空/满 */
            uart2_rb.buf[uart2_rb.head] = byte;
            uart2_rb.head = next;
        }                                           /* else: 缓冲满, 丢弃并可在主循环告警 */
    }
    if (USART2->SR & USART_SR_ORE) {               /* 溢出错误: 见 4.6 节, 必须显式清除 */
        (void)USART2->SR;
        (void)USART2->DR;
    }
}

/* 主循环消费: 返回实际读取的字节数 */
int uart2_read(uint8_t *dst, int maxlen)
{
    int n = 0;
    while (n < maxlen && uart2_rb.tail != uart2_rb.head) {
        dst[n++] = uart2_rb.buf[uart2_rb.tail];
        uart2_rb.tail = (uart2_rb.tail + 1) & (UART_RB_SIZE - 1);
    }
    return n;
}

/* 阻塞发送: 先填数据寄存器(TXE), 最后等移位完成(TC) */
void uart2_write(const uint8_t *data, int len)
{
    while (len--) {
        while (!(USART2->SR & USART_SR_TXE)) { }   /* 等待发送寄存器空 */
        USART2->DR = *data++;
    }
    while (!(USART2->SR & USART_SR_TC)) { }        /* 等待最后一位移出芯片 */
}

配套的中断使能（CubeMX 勾选 USART2 全局中断即可，或代码里 __HAL_UART_ENABLE_IT(&huart2, UART_IT_RXNE); HAL_NVIC_EnableIRQ(USART2_IRQn);）。主循环里以 uart2_read(buf, sizeof buf) 非阻塞取数，取到后交给协议解析状态机。这套结构覆盖 90% 的中低速串口需求，请务必亲手敲一遍并烧板验证。

4.5 DMA + 空闲中断：不定长接收的正解

GPS 报文、数传帧、Modbus 帧——长度不固定、字节间隔不均匀。逐字节中断在 921600 波特率下每 11 μs 进一次中断，CPU 不堪重负；而「DMA 收满固定长度再通知」又对不定长帧无能为力。解法是 IDLE（空闲）检测：串口检测到总线空闲超过 1 个字节时间，硬件自动置 IDLE 标志并触发中断——一次中断 = 一帧完整的报文。新版 HAL 把「DMA + IDLE」封装成了一个 API：

/* ============ 初始化: 启动一次, 之后由回调自我续期 ============ */
#define RX_DMA_SIZE 128
static uint8_t rx_dma_buf[RX_DMA_SIZE];        /* DMA 缓冲: 不能放 CCM(见第8/9章) */

void uart_start_idle_rx(void)
{
    /* 半满/全满/空闲 任一事件都会触发回调, Size=已收字节数 */
    HAL_UARTEx_ReceiveToIdle_DMA(&huart2, rx_dma_buf, RX_DMA_SIZE);
    /* 若只想要"整帧"通知, 可关掉半满中断: */
    /* __HAL_DMA_DISABLE_IT(huart2.hdmarx, DMA_IT_HT); */
}

/* ============ 回调: 每收完一帧(或缓冲满)进入一次 ============ */
void HAL_UARTEx_RxEventCallback(UART_HandleTypeDef *huart, uint16_t Size)
{
    if (huart == &huart2) {
        frame_process(rx_dma_buf, Size);          /* Size = 本帧字节数 */
        HAL_UARTEx_ReceiveToIdle_DMA(&huart2, rx_dma_buf, RX_DMA_SIZE);  /* 重新武装 */
    }
}

工作过程可以画成：DMA 在后台把字节搬进 rx_dma_buf → 报文发完, 总线静默 1 字节时间 → 硬件置 IDLE → 进一次回调, Size 即帧长 → 处理后重启 DMA。有三个细节决定可靠性：其一，帧间隔若小于 1 字节时间（连续流数据），IDLE 不会触发，靠半满/全满中断兜底；其二，frame_process 在中断上下文执行，长处理应拷贝数据后交主循环或投递到队列；其三，处理与重启之间的字节会丢——严格不丢帧的应用改用「双缓冲/乒乓」或循环模式 + 读指针方案（思想同 8.5 节）。

5. SPI：高速同步总线的正确用法

SPI（Serial Peripheral Interface）以「有时钟线、主从架构、全双工交换」三个特征区别于 UART，速率可达数十 Mbps，是 IMU、Flash、屏幕、ADC 等高速芯片的标准接口。它的坑集中在两个概念：CPOL/CPHA 四种模式与「读也是写」的全双工本质。

5.1 协议原理：四线、四模式与全双工交换

四根信号线各司其职：SCK（时钟，主机产生）、MOSI（主出从入）、MISO（从出主入）、CS/NSS（片选，主机拉低选中目标）。与 UART 的关键差异：SPI 有时钟线，每位在时钟边沿上对齐，因此没有波特率误差问题，速度上限只受电气特性约束。

CPOL（Clock Polarity，空闲电平）与 CPHA（Clock Phase，采样边沿）组合出四种模式，通信双方必须一致：

模式 CPOL CPHA 采样发生在 典型器件
Mode 0 0（空闲低） 0 SCK 第一个（上升）边沿 W25Q Flash、多数传感器
Mode 1 0 1 SCK 第二个（下降）边沿 少数 TFT 屏
Mode 2 1（空闲高） 0 SCK 第一个（下降）边沿 少见
Mode 3 1 1 SCK 第二个（上升）边沿 SD 卡 SPI 模式、MPU9250 可选

「全双工交换」是理解一切 SPI 代码的钥匙：主机与从机各有一个 8 位移位寄存器，首尾相连成一个 16 位环；主机发一个字节的同时，从机的字节被顶进来。因此「读一个字节」=「发一个无意义的 dummy 字节来产生时钟」。而多从机共享同一组 MISO/MOSI/SCK，用各自的 CS 区分——同一时刻只能有一个 CS 有效，且 MOSI/MISO 在非选中器件侧呈高阻。

5.2 STM32 SPI 外设要点

  • 速率：主模式下 SCK = 所在总线时钟 / (2, 4, 8, …, 256)。F407 的 SPI1 挂 APB2（84 MHz）最高 42 Mbps；SPI2/3 挂 APB1（42 MHz）最高 21 Mbps。选外设时先看它挂在哪条总线。
  • NSS 引脚：硬件 NSS 只适合「单一从机且从机支持被硬件选中」的场景，实际工程几乎都用 软件片选——任意 GPIO 拉低/拉高，控制自由（如先发命令再拉高）且规避硬件 NSS 时序限制。CubeMX 里 NSS 选 Disable，CS 配成 GPIO_Output。
  • FIFO：F4 的 SPI 无 FIFO（一次一个字节，高速率下 CPU 需持续喂）；F7/H7 的 SPI 带 16 字节 FIFO，配 DMA 后高速传输 CPU 占用骤降。
  • 帧格式：支持 8/16 位帧（F4），H7 可配到 32 位。8 位帧最通用。

5.3 基础驱动：寄存器读写模板

绝大多数 SPI 传感器遵循同一套寄存器模型：第一个字节 = 寄存器地址（最高位 1 表示读、0 表示写，具体看器件手册），后续字节 = 数据。把这套模板写熟，换任何 SPI 器件只改命令位约定：

/* spi_dev.c —— SPI 器件寄存器读写模板 (软件片选) */
#define CS_LOW()   HAL_GPIO_WritePin(CS_GPIO_Port, CS_Pin, GPIO_PIN_RESET)
#define CS_HIGH()  HAL_GPIO_WritePin(CS_GPIO_Port, CS_Pin, GPIO_PIN_SET)

/* 全双工交换 1 字节: 发 tx 的同时收回 rx —— SPI 读写都是"交换" */
static uint8_t spi_xfer_byte(uint8_t tx)
{
    uint8_t rx;
    HAL_SPI_TransmitReceive(&hspi1, &tx, &rx, 1, 20);
    return rx;
}

uint8_t imu_read_reg(uint8_t reg)   /* 例: imu_read_reg(0x75) 读 WHO_AM_I */
{
    uint8_t val;
    CS_LOW();
    spi_xfer_byte(reg | 0x80);      /* 地址字节, MSB=1 表示读 */
    val = spi_xfer_byte(0x00);      /* dummy 字节产生时钟, 收回寄存器值 */
    CS_HIGH();                       /* 必须在完整字节边界后拉高 */
    return val;
}

void imu_write_reg(uint8_t reg, uint8_t val)
{
    CS_LOW();
    spi_xfer_byte(reg & 0x7F);      /* MSB=0 表示写 */
    spi_xfer_byte(val);
    CS_HIGH();
}

/* 连续读多字节(地址自动+1): FIFO/批量采样用 */
void imu_read_regs(uint8_t reg, uint8_t *buf, uint16_t len)
{
    CS_LOW();
    spi_xfer_byte(reg | 0x80);
    for (uint16_t i = 0; i < len; i++)
        buf[i] = spi_xfer_byte(0x00);
    CS_HIGH();
}

上电自检三板斧：读 WHO_AM_I 核对器件 ID → 写一个配置寄存器再读回核对 → 读数据寄存器看数值合理性。三步全过再往下写驱动，能把排障范围瞬间缩小一半。

5.4 DMA 高速传输：以 W25Q Flash 为例

轮询收发在 42 Mbps 下每字节约 190 ns，CPU 根本来不及喂——命令与地址段（几个字节）用轮询没问题，大块数据段必须交给 DMA。以 W25Q128 读数据为例（命令 0x03 + 24 位地址 + 连续数据流）：

/* 命令+地址段很短, 轮询发送; 数据段长, 交给 DMA */
void w25q_read(uint32_t addr, uint8_t *rx, uint16_t len)
{
    uint8_t cmd[4] = { 0x03,
                       (uint8_t)(addr >> 16), (uint8_t)(addr >> 8), (uint8_t)addr };

    CS_LOW();
    HAL_SPI_Transmit(&hspi1, cmd, 4, 20);            /* 轮询发命令+地址 */
    HAL_SPI_Receive_DMA(&hspi1, rx, len);              /* DMA 后台收数据 */
    while (HAL_SPI_GetState(&hspi1) != HAL_SPI_STATE_READY) { }  /* RTOS 下换信号量等待 */
    CS_HIGH();                                          /* 时序: 必须等 DMA+SPI 全部收尾 */
}

两点深化：其一，「等待完成」在裸机里可以用 HAL_SPI_GetState 轮询（如上），在 RTOS 里应换成「TxCplt/RxCplt 回调里释放信号量」，把 CPU 还给其他任务；其二，全双工高速场景（如同时刷新屏幕 + 回读状态）用 HAL_SPI_TransmitReceive_DMA 一次搞定，且发送缓冲必须是整个传输期间不可改动的内存（DMA 在后台读它）。SPI 的 DMA 同样受「缓冲区位置」约束（第 8、9 章），CCM 内存里的缓冲区对 DMA 不可见。

6. I2C：两线总线的坑与解法

I2C（Inter-Integrated Circuit）用两根开漏线（SCL 时钟 + SDA 数据）挂起一串低速器件，省引脚、可热插拔多设备，代价是时序复杂、总线易卡死。它是三个常用串行接口里协议最「讲规矩」的一个，也是新手故障率最高的一个——本章把规矩讲透，把卡死的解法给全。

6.1 协议原理：起始位、应答与地址

I2C 特点：SDA 只允许在 SCL 低电平期间变化（SCL 高时的 SDA 跳变被定义为起始/停止条件）；数据高位在前；每传一个字节，接收方必须回一个 ACK（第 9 位拉低表示应答）。

  起始条件: SCL 高时 SDA 由高→低        停止条件: SCL 高时 SDA 由低→高
  SCL  ──▔▔▔╲___________                 SCL  ──────▔▔▔╲____▔▔▔
  SDA  ──▔▔╲_____________                SDA  ──────______╱▔▔▔▔

  一次完整读操作 (7 位地址):
  [S] [地址+写] [ACK] [寄存器号] [ACK] [Sr=重复起始] [地址+读] [ACK] [数据] [NACK] [P]
   │      │            │                     │             │
   │   0x68<<1|0       │                  0x68<<1|1      主机最后不发ACK表示读完了
   └── 地址字节 = 7位地址左移1位 + 读写位(0写/1读)

两个必须刻进肌肉记忆的细节：其一，7 位地址 0x68（MPU6050）在线上是 0x68 << 1 | 读写位，HAL 库的地址参数就要求传入已左移的 8 位地址——直接填 0x68 会访问 0x34。其二，I2C 有「时钟拉伸（Clock Stretching）」机制：从机没准备好时可以按住 SCL 拉低不放，强制主机等待——这是 I2C 区别于 SPI 的流控机制，也意味着 SCL 卡低可能是从机的合法行为。

6.2 STM32 的两种 I2C 外设：旧 IP 与新版 IP

维度 旧版 I2C（F1/F2/F4 等多数 F 系列） 新版 I2C（F0/F3/F7/G0/G4/H7/L4+）
时序配置 CCR + TRISE 寄存器，按公式手算 TIMINGR 寄存器一个值搞定，CubeMX 自动生成
事件模型 标志位序列（SB → ADDR → BTF …），驱动难写，状态机臭名昭著 TISR 统一事件中断，驱动干净

F4 用户（本手册主线）的最佳实践：旧版 I2C 外设只用 HAL 的阻塞 API（HAL_I2C_Mem_Read/Write），把 I2C 速率压在 100–400 kHz，大事化小；确实需要高吞吐 I2C（如 OLED 刷屏）时选 F7/G4/H7 新版 IP，或干脆换成 SPI 屏。

6.3 阻塞式驱动模板与典型器件

HAL 的 Mem_Read/Mem_Write 把「地址 + 寄存器 + 数据」的完整事务封装好，是 90% 场景的最优解。两个典型器件示例：

/* 例1: 读 MPU6050 的 WHO_AM_I (寄存器 0x75, 期望 0x68) */
#define MPU6050_ADDR (0x68 << 1)     /* HAL 要已左移的 8 位地址 */

uint8_t mpu_who_am_i(void)
{
    uint8_t id = 0;
    HAL_I2C_Mem_Read(&hi2c1, MPU6050_ADDR, 0x75,
                     I2C_MEMADD_SIZE_8BIT, &id, 1, 100);   /* 100ms 超时 */
    return id;
}

/* 例2: AT24C02 EEPROM 页写 —— I2C 器件"写完要等待"的教科书案例 */
void at24c02_write(uint8_t word_addr, const uint8_t *buf, uint8_t len)
{
    /* 页写单次最多 8 字节且不能跨页, 超出会回卷覆盖页首 */
    HAL_I2C_Mem_Write(&hi2c1, 0x50 << 1, word_addr,
                      I2C_MEMADD_SIZE_8BIT, (uint8_t *)buf, len, 100);
    HAL_Delay(5);      /* 内部写周期 tWR ≈ 5ms: 期间器件不应答, 不等必失败 */
}

读回校验的习惯同样适用于 I2C：HAL_I2C_Mem_Read 的返回值是 HAL_StatusTypeDef，必须检查——返回 HAL_ERROR 往往意味着总线上没有器件应答（NACK），是排查接线与地址的第一手信息。

6.4 总线卡死的检测与恢复

I2C 最著名的故障是「总线卡死」：主机在传输中途复位（或丢时钟），从机还停在「正在发数据第 n 位」的状态，继续把 SDA 按在低电平等时钟；主机重新上电后看到 SDA 一直为低，任何 START 都发不出来。检测方法：SCL 为高时读 SDA，若持续为低即为卡死。恢复方法是业界标准九时钟法：

/* i2c_recover.c —— I2C 总线卡死恢复 (九时钟法) */
void i2c_bus_recover(void)
{
    GPIO_InitTypeDef g = {0};

    HAL_I2C_DeInit(&hi2c1);                          /* 1) 先放手, 外设退出总线 */

    /* 2) SCL 切成普通开漏 GPIO, 由 CPU 手动打时钟 */
    g.Pin = SCL_Pin;  g.Mode = GPIO_MODE_OUTPUT_OD;
    g.Pull = GPIO_PULLUP;  g.Speed = GPIO_SPEED_FREQ_LOW;
    HAL_GPIO_Init(SCL_GPIO_Port, &g);

    for (int i = 0; i < 9; i++) {                /* 3) 最多 9 个脉冲: 覆盖 1 字节+ACK */
        HAL_GPIO_WritePin(SCL_GPIO_Port, SCL_Pin, GPIO_PIN_RESET);
        for (volatile int d = 0; d < 200; d++) { }   /* 半周期延时(约5us @100kHz) */
        HAL_GPIO_WritePin(SCL_GPIO_Port, SCL_Pin, GPIO_PIN_SET);
        for (volatile int d = 0; d < 200; d++) { }
        if (GPIO_PIN_SET == HAL_GPIO_ReadPin(SDA_GPIO_Port, SDA_Pin))
            break;                                   /* SDA 释放即可提前结束 */
    }

    /* 4) 补一个 STOP: SCL 高电平期间 SDA 由低→高, 让从机回到空闲态 */
    g.Pin = SDA_Pin;  HAL_GPIO_Init(SDA_GPIO_Port, &g);
    HAL_GPIO_WritePin(SDA_GPIO_Port, SDA_Pin, GPIO_PIN_RESET);
    HAL_GPIO_WritePin(SCL_GPIO_Port, SCL_Pin, GPIO_PIN_SET);
    HAL_GPIO_WritePin(SDA_GPIO_Port, SDA_Pin, GPIO_PIN_SET);

    HAL_I2C_Init(&hi2c1);                            /* 5) 重新接管总线 */
}

原理：从机最多只会持续输出一个字节（8 位）加一个应答位，打满 9 个时钟后它的移位寄存器必然走完，SDA 自然释放。工程上把「上电初始化时检测一次 + 通信连续 N 次失败后恢复一次」写成标准流程，I2C 的现场死机率能降一个数量级。

7. CAN 与 CAN FD：从总线协议到 FDCAN 驱动

CAN 是车载与工业控制的主干总线，也是多节点「共享一条线还能不打架」的典范设计。本章先讲透经典 CAN 的仲裁与错误管理（这是理解一切 CAN 现象的钥匙），再讲 CAN FD 的增强点，最后给出 STM32 两代 CAN 外设（bxCAN 与 FDCAN）的完整驱动代码与位时序计算方法。

7.1 经典 CAN 协议基础

CAN 用一对差分线（CAN_H / CAN_L）传输，显性电平（逻辑 0）与隐性电平（逻辑 1）的判定靠两线压差：显性压差大、隐性压差约等于零。多个节点同时往总线上「写 0」，总线上就是 0——这个「线与」特性是一切仲裁的基础。

逐位仲裁：所有节点同一时刻开始发帧，每一位都把电平写上总线再读回来比较——如果自己写的是 1（隐性）而读回 0（显性），说明有更高优先级的帧在发，自己立刻退出转为接收。ID 数值越小优先级越高，且仲裁是非破坏性的：赢家一比特都不用重发。这就是 CAN 不需要交换机、集线器也能多主运行的原因。

数据帧结构（标准帧）：

字段 长度 含义
SOF 1 位 帧起始，显性
Identifier 11 位（扩展帧 29 位 = 11 + 18） 报文 ID；既是优先级也是内容分类符（「这是姿态数据」而不是「这是某节点发的」）
RTR 1 位 数据帧（显性）/ 遥控帧（请求远端发送）
DLC 4 位 数据长度 0–8 字节
Data 0–8 字节 经典 CAN 单帧上限 8 字节（CAN FD 扩到 64）
CRC + ACK + EOF 约 16+2+7 位 CRC 校验；ACK 槽：任何收到且校验通过的节点显性应答

位填充：连续 5 个相同电平后自动插入 1 个反向电平，保证每个位边界都有跳变供接收方同步。这意味着「实际总线占用时间比理论位时间多」，计算总线负载率时要留余量。

错误管理是 CAN 可靠性的核心，也是现场调试 60% 问题的出处。每个节点维护两个计数器：TEC（发送错误计数）与 REC（接收错误计数），并按计数在三种状态间流转：

  Error Active (TEC<128 且 REC<128)         正常态: 可主动发"错误帧"打断总线
      │ 错误计数涨到 128
      ▼
  Error Passive (任一 ≥128)                 被动态: 只能发隐性错误标志, 不再干扰别人
      │ TEC ≥ 256
      ▼
  Bus-Off (TEC ≥ 256)                       与总线隔离: 不发不应, 等待恢复

  计数规则速记: 发送失败 +8;  发送成功 -1;  接收出错 +1(或更多);  接收成功 -1

7.2 CAN FD：增强在哪里

CAN FD（Flexible Data-rate）在保持仲裁机制不变的前提下做了三件事：

增强点 经典 CAN CAN FD 意义
数据段变速（BRS 位） 全程一个速率（典型 500 kbps / 1 Mbps） 仲裁段慢速（保证多节点同步），数据段加速（典型 2–5 Mbps） 小 ID 头 + 高速数据，吞吐提升数倍
数据段加长 8 字节 64 字节（DLC 编码 9–15 对应 12/16/20/24/32/48/64） UDS 诊断、固件刷写、日志传输单帧搞定

7.4 位时序计算：仲裁段与数据段各算一遍

CAN 的位时间被切成若干「时间量子」（Tq，Time Quantum），采样点在位中间偏后：

 一个位时间 (以 F407 经典 CAN 500 kbps 为例: APB1=42 MHz, 分频 6, 共 14 Tq)
 |◄─SYNC(固定1Tq)─►|◄──────BS1: 11 Tq──────►|◄─BS2: 2 Tq─►|
 ▲                                                        ▲
 位起点                                                  位终点
                              ▲ 采样点 = (1+11)/14 ≈ 85.7%

 位速率 = 总线时钟 / (分频 × Tq总数) = 42 MHz / (6 × 14) = 500 kbps
 采样点推荐区间 75% ~ 87.5% (车载常用 80% ~ 87.5%)

配置思路是从波特率反推 Tq 总数，再把 Tq 分给 BS1/BS2 以落准采样点。经典 CAN 与 FDCAN 各给一组实例：

场景 时钟 分频 Tq 数（1 + BS1 + BS2） 波特率 采样点
F407 经典 CAN 500 k 42 MHz（APB1） 6 1 + 11 + 2 = 14 500 kbps 85.7%
F407 经典 CAN 1 M 42 MHz 3 1 + 10 + 3 = 14 1 Mbps 78.6%
G4/H7 FDCAN 仲裁段 500 k 80 MHz（内核时钟） 10 1 + 13 + 2 = 16 500 kbps 87.5%
G4/H7 FDCAN 数据段 5 M 80 MHz 2 1 + 6 + 1 = 8 5 Mbps 87.5%
G4/H7 FDCAN 数据段 2 M 80 MHz 2 1 + 16 + 3 = 20 2 Mbps 85%

实践要点：全网所有节点的波特率与采样点必须一致（采样点差几个百分点，长帧就会在累计相位误差下出错）；CAN 位速率对时钟源精度的要求是 0.5% 以内，因此 CAN 必须用外部晶振（1.5 节）；CubeMX 的 FDCAN 配置页会实时显示算得的波特率与采样点，先在配置页对表、再对照手册复核，是双手保险。配置完用 CAN 分析仪（TSMaster / CANoe /CANable）回读实际位时序验证，与台架测试流程一致。

7.5 bxCAN 驱动完整模板（F407）

把过滤器、发送、接收三块拼齐。过滤器是 bxCAN 的第一道坎：不过滤器默认不接收任何报文（收不到报文先查过滤器，其次查总线上有没有其他节点给 ACK）。

/* can_bx.c —— F407 bxCAN 完整收发模板 */

/* ① 过滤器: CAN1 用过滤器组 0, 32 位掩码模式, 只收标准帧 0x300~0x3FF */
static void can_filter_config(void)
{
    CAN_FilterTypeDef f = {0};
    f.FilterBank           = 0;                    /* 组号 0~27; 双 CAN 时 CAN2 必须用 14 以后 */
    f.FilterMode           = CAN_FILTERMODE_IDMASK;
    f.FilterScale          = CAN_FILTERSCALE_32BIT;
    /* 32 位模式寄存器布局: [31:21]=STID(11位标准ID), 因此 16 位高半字要左移 5 位 */
    f.FilterIdHigh         = (uint16_t)(0x300 << 5);   /* 期望 ID = 0x300 */
    f.FilterIdLow          = 0;
    f.FilterMaskIdHigh     = (uint16_t)(0x700 << 5);   /* 掩码: 只比 ID 高 3 位 → 0x300~0x3FF 全收 */
    f.FilterMaskIdLow      = 0;                    /* 低 16 位(含 RTR/IDE)不参与比较 */
    f.FilterFIFOAssignment = CAN_RX_FIFO0;
    f.FilterActivation     = ENABLE;
    HAL_CAN_ConfigFilter(&hcan1, &f);
}

/* ② 启动 + 打开 FIFO0 收报中断 */
void can_start(void)
{
    can_filter_config();
    HAL_CAN_Start(&hcan1);
    HAL_CAN_ActivateNotification(&hcan1, CAN_IT_RX_FIFO0_MSG_PENDING);
}

/* ③ 发送: 硬件 3 个邮箱是宝贵的发送队列, 满了就显式拒绝(别覆盖) */
HAL_StatusTypeDef can_send(uint16_t std_id, const uint8_t *data, uint8_t len)
{
    CAN_TxHeaderTypeDef tx = {0};
    uint32_t mailbox;

    if (HAL_CAN_GetTxMailboxesFreeLevel(&hcan1) == 0)
        return HAL_BUSY;               /* 总线繁忙(仲裁失败/无ACK重发)时邮箱会被占满 */

    tx.StdId = std_id;
    tx.IDE   = CAN_ID_STD;
    tx.RTR   = CAN_RTR_DATA;
    tx.DLC   = len;
    return HAL_CAN_AddTxMessage(&hcan1, &tx, (uint8_t *)data, &mailbox);
}

/* ④ 接收: 硬件 FIFO0 只有 3 帧深, 中断里必须尽快搬空 → 接力到软件队列 */
void HAL_CAN_RxFifo0MsgPendingCallback(CAN_HandleTypeDef *hcan)
{
    CAN_RxHeaderTypeDef rx;
    uint8_t data[8];

    while (HAL_CAN_GetRxMessage(&hcan1, CAN_RX_FIFO0, &rx, data) == HAL_OK) {
        msg_t m;
        m.id  = rx.StdId;
        m.len = rx.DLC;
        memcpy(m.data, data, m.len);
        queue_push(&can_rx_q, &m);      /* 软件 FIFO(环形队列, 见4.4节)供主循环消费 */
    }
}

模板要点：硬件 FIFO 深 3 帧是硬约束——1 Mbps 下 3 帧报文约 0.5 ms 就会灌满，中断若被更高优先级阻塞超过这个时间，报文将溢出丢失（bxCAN 有 FOV 溢出标志可查）。所以「中断接力软件队列」不是可选项，是必需品。

7.6 FDCAN 驱动模板（G4/H7）

FDCAN 的额外工作是把消息 RAM 划分清楚（过滤器几个、FIFO 几帧、Tx 几个），划分不够会直接收不到报文。以「仲裁 500 k + 数据 2 M，收 0x300~0x30F，发 FD 帧」为例：

/* ① 初始化要点(CubeMX 骨架之上的关键参数, 以 80MHz FDCAN 内核时钟为例) */
hfdcan1.Init.FrameFormat        = FDCAN_FRAME_FD_BRS;  /* FD 帧, 数据段变速 */
hfdcan1.Init.NominalPrescaler   = 10;   /* 仲裁段: 80M/10=8MHz, Seg1=13, Seg2=2 */
hfdcan1.Init.NominalTimeSeg1    = 13;   /* 500 kbps, 采样点 (1+13)/16=87.5% */
hfdcan1.Init.NominalTimeSeg2    = 2;
hfdcan1.Init.DataPrescaler      = 2;    /* 数据段: 80M/2=40MHz, Seg1=16, Seg2=3 */
hfdcan1.Init.DataTimeSeg1       = 16;   /* 2 Mbps, 采样点 (1+16)/20=85% */
hfdcan1.Init.DataTimeSeg2       = 3;

HAL_FDCAN_Init(&hfdcan1);

f.IdType       = FDCAN_STANDARD_ID;
f.FilterIndex  = 0;
f.FilterType   = FDCAN_FILTER_MASK;
f.FilterConfig = FDCAN_FILTER_TO_RXFIFO0;

/* ③ 启动 + 通知 */
HAL_FDCAN_Start(&hfdcan1);

/* ④ 发送一帧 CAN FD (64 字节, 数据段变速) */
HAL_StatusTypeDef fdcan_send64(uint32_t std_id, const uint8_t *data)
{
    FDCAN_TxHeaderTypeDef tx = {0};
    tx.Identifier  = std_id;
    tx.IdType      = FDCAN_STANDARD_ID;
    tx.TxFrameType = FDCAN_DATA_FRAME;
    tx.DataLength  = FDCAN_DLC_BYTES_64;
    tx.FDFormat    = FDCAN_FD_CAN;        /* FD 帧; 经典帧用 FDCAN_CLASSIC_CAN */
    tx.BitRateSwitch = FDCAN_BRS_ON;       /* 数据段变速; FDCAN_BRS_OFF 则全程仲裁段速率 */

/* ⑤ DLC 编码值 → 实际字节数: CAN FD 的 9~15 不等于长度, 必须查表 */
static const uint8_t dlc_to_len[16] =
    { 0,1,2,3,4,5,6,7,8,12,16,20,24,32,48,64 };

void HAL_FDCAN_RxFifo0Callback(FDCAN_HandleTypeDef *hfdcan, uint32_t its)
{
    FDCAN_RxHeaderTypeDef rx;
    uint8_t data[64];

    if (its & FDCAN_IT_RX_FIFO0_NEW_MESSAGE) {
        while (HAL_FDCAN_GetRxMessage(hfdcan, FDCAN_RX_FIFO0, &rx, data) == HAL_OK) {
            uint8_t len = dlc_to_len[rx.DataLength & 0x0F];
            msg_t m = { .id = rx.Identifier, .len = len };
            memcpy(m.data, data, len);
            queue_push(&can_rx_q, &m);
        }
    }
}

7.7 错误管理与 BUS-OFF 恢复

CAN 的错误态是设计出来的自愈机制，固件必须配合：节点发错时不出声「装死」，而是按 7.1 节的计数规则退避。固件侧要做的是监控 + 主动恢复。bxCAN 的 Bus-Off 默认不会自动恢复（依赖软件重启），FDCAN 可配置自动恢复但工程上通常也用软件管理以便记录事件：

/* 周期健康检查: 主循环每秒调用 */
void can_health_check(void)
{
    uint32_t err = HAL_CAN_GetError(&hcan1);

    /* 读原始错误计数, 上报遥测: ESR 寄存器 [23:16]=TEC, [15:8]=REC */
    uint32_t esr = hcan1.Instance->ESR;
    telemetry_set("can_tec", (esr >> 16) & 0xFF);
    telemetry_set("can_rec", (esr >> 8)  & 0xFF);

    if (err & HAL_CAN_ERROR_BOF) {          /* Bus-Off: TEC≥256, 已被隔离 */
        log_event(LOG_CAN_BUSOFF);          /* 先记录(黑匣子), 再恢复 */
        HAL_CAN_Stop(&hcan1);
        HAL_Delay(2);                       /* 协议要求恢复序列含 128×11 个隐性位的时间窗 */
        HAL_CAN_Start(&hcan1);
        HAL_CAN_ActivateNotification(&hcan1, CAN_IT_RX_FIFO0_MSG_PENDING);
    }
}

8. DMA：让数据搬运脱离 CPU

DMA（Direct Memory Access，直接内存访问）是一个专职「搬数据」的硬件引擎：CPU 只下一条指令（源、目的、长度），数据搬运就由 DMA 控制器在后台完成，搬完发一个中断。它是「高速外设 + 实时系统」的标配——ADC 连续采样、串口收帧、屏幕刷显存，背后都是 DMA。本章的重点不是「怎么开 DMA」（CubeMX 两个勾），而是三个真正决定成败的问题：缓冲区放在哪块内存（可达性）、数据到底搬没搬对（宽度与对齐）、搬完 CPU 读到的是不是新的（缓存一致性）。

8.1 为什么需要 DMA：总线视角

Cortex-M 系列的芯片内部是一片「总线矩阵」，CPU、DMA、各外设都是矩阵上的主设备（Master），Flash 与 SRAM 是从设备（Slave）。以 F407 为例：

                     ┌──────────── 总线矩阵 BusMatrix ────────────┐
  Cortex-M4 CPU      │                                            │
  ├─ I-Bus ─────────►│─► Flash (代码区, 0x08000000)                │
  ├─ D-Bus ─────────►│─► SRAM1/SRAM2 (0x20000000, 128K)           │
  └─ S-Bus           │                                            │
  DMA1 (8 Stream) ──►│──► APB1 / APB2 / AHB1 外设端口              │
  DMA2 (8 Stream) ──►│      (UART/SPI/I2C/ADC/TIM 寄存器/数据口)   │
                     │                                            │
                     │  ※ DMA1/DMA2 到不了 CCM (0x10000000) !      │
                     └────────────────────────────────────────────┘
 DMA 与 CPU 竞争同一条 SRAM 总线: 仲裁按 DMA 优先级 > CPU(通常), 大批量搬运会"偷走"总线带宽

这个视角直接导出三条工程规律：其一，DMA 不是零成本的——搬运期间 CPU 的取指与访存会与 DMA 仲裁，大批量 M2M 搬运会拖慢 CPU（反之亦然）；其二，缓冲区「放在哪」先于「怎么配」——放错内存区域，DMA 静默不工作（下一节）；其三，实时性设计要把「搬运流量」算进总线预算，而不是只算 CPU 周期。

8.2 可达性矩阵：缓冲区放错位置，DMA 就是哑的

这是 DMA 篇最重要的知识点。STM32 的不同内存区域「挂在不同的总线上」，DMA 控制器只能访问它总线能到达的区域——访问不可达区域不会报错，DMA 直接静默失败，缓冲区里什么都没有，排查起来极其隐蔽：

内存区域 地址（F407 / H743） F407 DMA1/DMA2 H7 DMA1/DMA2（D2 域） H7 MDMA
主 Flash 0x08000000 可读 可读 可
主 SRAM（F4 的 SRAM1/2，128 K） 0x20000000 可（默认去处） —（H7 该地址是 DTCM） —
CCM（F4 的 64 K CPU 专用 RAM） 0x10000000 不可（高频翻车点） — —
DTCM（H7 的 128 K 全速 RAM） 0x20000000 — 不可（默认链接到这，DMA 却够不着！） 可
AXI SRAM（H7 的 512 K） 0x24000000 — 可 可
D2 域 SRAM1/2/3（H7 的 288 K） 0x30000000 — 可 可
D3 域 SRAM4（H7 的 64 K） 0x38000000 — 不可（D3 只有 DMA3/DMA4 与 MDMA 能到） 可

两张「必背」结论卡：F407——所有 DMA 缓冲放 0x20000000 的主 SRAM，别放 CCM；H743——默认全局变量被链接到 DTCM，而 D2 域的 DMA1/DMA2 到不了 DTCM，DMA 缓冲必须显式挪到 AXI SRAM（0x24000000）或 D2 SRAM（0x30000000），或改用 MDMA。检查手段：看 map 文件里缓冲区实际地址，对号入座。

8.3 核心配置项逐个看懂

F4 的 DMA 是「控制器 × 8 Stream」结构，每个 Stream 就是一条独立搬运流水线。CubeMX 生成的配置里每个字段都对应一个物理行为：

配置项 取值 物理含义与选择依据
Direction P2M / M2P / M2M 外设→内存（接收）/ 内存→外设（发送）/ 内存→内存（只有 DMA2 支持 M2M）
Peripheral Increment Enable / Disable 外设地址是否自增——外设数据寄存器只有一个，永远 Disable
Memory Increment Enable / Disable 内存地址自增——存进/取自缓冲区数组，几乎总是 Enable
Data Width（外设/内存） Byte / Half Word / Word 与外设数据寄存器宽度一致（UART 是 Byte，ADC 12 位对齐后可 Half Word）；两侧宽度可不同（窄进宽出自动打包，如 4×byte 打包成 1×word 减少总线访问次数）
Mode Normal / Circular Normal 搬完即停；Circular 循环模式——搬完自动回卷重新开始，连续采集（ADC 流、串口流）必选
FIFO / Burst Disable / FIFO 模式 + 突发长度 F4 的每个 Stream 带 4 字 FIFO：FIFO + 突发（一次搬 4/8/16 个单位）能显著减少总线仲裁次数，高带宽场景（LCD、摄像头）必开；小流量直接模式即可
Priority VeryHigh → Low 同控制器内多 Stream 仲裁用；原则「实时性要求越高优先级越高」，但把所有流都设 VeryHigh 等于都没设
中断 TC / HT / TE 全满（Transmission Complete）/ 半满（Half Transfer）/ 错误。半满 + 全满 = 乒乓处理的基本盘（8.5 节）

另一个隐形约束是请求映射表：F4 上「哪个外设能接到哪个 DMA 的哪个 Stream」是芯片设计时定死的（例如 ADC1 只能接 DMA2 的 Stream0/Stream4，USART2_RX 只能接 DMA1 的 Stream5）。CubeMX 会自动选，但多路 DMA 冲突时需要查参考手册 RM0090 的 DMA 请求映射表手工挪位置。

8.4 循环模式 + 半满/全满：乒乓处理完整模板

连续数据流（ADC 每微秒一个采样点）的经典问题：DMA 在写的缓冲区，CPU 同时在处理——读一半时数据被改写怎么办？答案是乒乓（Ping-Pong）：把循环缓冲从中间分开，DMA 写后半时 CPU 处理前半，DMA 回卷写前半时 CPU 处理后半，半满/全满两个中断正好是「交接棒」的时刻：

/* adc_pingpong.c —— ADC 连续采样 + DMA 循环 + 乒乓处理 */
#define ADC_BUF_LEN 512            /* 半缓冲长度, 总缓冲 2×512 */
static uint16_t adc_buf[2 * ADC_BUF_LEN];   /* 必须在 DMA 可达区域(8.2节)! */

void adc_stream_start(void)
{
    /* CubeMX 已配: DMA2-Stream0, Circular, HalfWord, 半满+全满中断 */
    HAL_ADC_Start_DMA(&hadc1, (uint32_t *)adc_buf, 2 * ADC_BUF_LEN);
}

/* 半满回调: DMA 正在写后半 [512..1023], 前半 [0..511] 是完整冻结的数据 */
void HAL_ADC_ConvHalfCpltCallback(ADC_HandleTypeDef *hadc)
{
    process_block(&adc_buf[0], ADC_BUF_LEN);      /* 滤波/FFT/均值, 尽快返回 */
}

/* 全满回调: DMA 已回卷写前半, 后半 [512..1023] 是完整冻结的数据 */
void HAL_ADC_ConvCpltCallback(ADC_HandleTypeDef *hadc)
{
    process_block(&adc_buf[ADC_BUF_LEN], ADC_BUF_LEN);
}

成立条件只有一条，也是唯一可能被破坏的约定：process_block 必须在半个缓冲的处理时限内完成（例如 512 点 @ 100 ksps = 5.12 ms），否则 DMA 回卷会把还没处理完的数据踩掉。超期检测可以在回调里比较处理耗时（DWT 周期计数，10.1 节），一旦超限立刻告警——这类「时序违约」在正常运行时绝不发生，只有负载突变时才暴露，必须有自监控。

8.5 缓存一致性（M7 专属，但必须提前学）

Cortex-M4 没有数据缓存（D-Cache），「DMA 写内存 → CPU 读内存」天然是最新数据。但 Cortex-M7（F7/H7）在 CPU 与内存之间加了缓存，问题随之而来：缓存里可能存着内存的旧拷贝：

 问题一 (DMA 发送):  CPU 改了 buf[0]=1 → 只改在 Cache 里, 内存里还是 0
                     → DMA 从内存搬运 → 把 0 发了出去 (发了旧数据!)

 问题二 (DMA 接收):  DMA 把新数据写进内存 → CPU 的 Cache 里还是旧值
                     → CPU 读 buf 读到 Cache 命中的旧数据 (读了旧数据!)

        CPU 核心          Cache (几行后述)          SRAM (真实存放处)
        ┌──────┐  读写   ┌─────────┐   回写      ┌─────────┐
        │ ALU  │◄───────►│ 拷贝副本 │ ─────不即时─►│ 真身数据 │◄──DMA 只认这里
        └──────┘         └─────────┘             └─────────┘

三种解法按推荐顺序：

解法一：缓存维护指令（最通用）。发送前把 Cache「清」（Clean，写回内存），接收前把 Cache「作废」（Invalidate，扔掉副本下次重读）：

/* 发送: Clean 把 CPU 在 Cache 里改的内容写回内存, DMA 才能拿到新数据 */
SCB_CleanDCache_by_Addr((uint32_t *)tx_buf, TX_LEN);
HAL_SPI_Transmit_DMA(&hspi1, tx_buf, TX_LEN);

/* 接收: Invalidate 丢掉 Cache 里的旧副本, CPU 下次读强制从内存取 DMA 写的新数据 */
SCB_InvalidateDCache_by_Addr((uint32_t *)rx_buf, RX_LEN);
HAL_SPI_Receive_DMA(&hspi1, rx_buf, RX_LEN);

关键细节：缓存行 32 字节对齐。Clean/Invalidate 以 32 字节缓存行为最小单位，操作范围会向上/向下取整到整行——如果缓冲区首尾紧挨着无关变量，作废操作会把邻居变量的 Cache 一并扔掉（安全），但发送 Clean 若邻居还没写回，可能把邻居「顺便」写回（无害）；真正危险的是 Invalidate 落在别人正在编辑的同一行上，丢掉的是别人的新数据。所以规范是：

static uint8_t dma_rx_buf[RX_LEN] __attribute__((aligned(32)));  /* 首对齐 */
/* 长度取整: RX_LEN 也应是 32 的倍数, 或末尾用填充凑齐 — 尾对齐 */

解法二：MPU 划一块非缓存区（最省心，推荐）。把一块内存整体配成 Non-cacheable，DMA 缓冲全放这里，彻底没有一致性问题，代价是 CPU 访问这块区域不走缓存略慢——对缓冲区来说通常无感：

/* 把 H7 的 SRAM4 (0x38000000, 64KB) 整块配为非缓存区, 专放 DMA 缓冲 */
void mpu_config_dma_region(void)
{
    MPU_Region_InitTypeDef m = {0};
    HAL_MPU_Disable();

    m.Enable            = MPU_REGION_ENABLE;
    m.Number            = MPU_REGION_NUMBER0;
    m.BaseAddress       = 0x38000000;
    m.Size              = MPU_REGION_SIZE_64KB;
    m.AccessPermission  = MPU_REGION_FULL_ACCESS;
    m.IsCacheable       = MPU_ACCESS_NOT_CACHEABLE;   /* 关键: 关缓存 */
    m.IsBufferable      = MPU_ACCESS_NOT_BUFFERABLE;
    m.IsShareable       = MPU_ACCESS_SHAREABLE;
    m.DisableExec       = MPU_INSTRUCTION_ACCESS_DISABLE;
    HAL_MPU_ConfigRegion(&m);
    HAL_MPU_Enable(MPU_PRIVILEGED_DEFAULT);
}
/* 之后把所有 DMA 缓冲的地址定在这块区域(链接脚本加段, 见 9.6 节), 一劳永逸 */

解法三：放 DTCM（H7 特供）。DTCM 不经过缓存，天然一致，且 CPU 全速访问——但它只有 MDMA 能访问（8.2 节），适合「MDMA 搬运 + CPU 高频处理」的场景。

9. 内存：地址空间、区域分配与碎片治理

内存管理是 MCU 开发从「能跑」到「稳跑」的分水岭。PC 上内存错误表现为崩溃；MCU 上表现为随机 HardFault、数据偶发错乱、运行数天后才复现的死机——问题与案发时间相隔十万八千里。本章回答四个问题：内存有哪些区域（地址空间与 STM32 内存地图）、变量怎么被放进内存（段与启动流程）、怎么把变量精确放到指定区域（链接脚本与属性）、以及为什么嵌入式慎用 malloc 并如何用内存池根治碎片；最后进阶走读 FreeRTOS 的默认堆实现 heap_4（9.7 节），看工业级通用分配器如何用「首次适配 + 空闲块合并」在通用性与实时性之间取平衡。

9.1 Cortex-M 的 4GB 地址空间地图

ARM 把 32 位地址空间预划分为几个大区，访问哪个区就是访问哪种资源——这是理解一切内存问题的坐标系：

 0x0000_0000 ┌──────────────────────────────────────────────┐
             │ 代码区: Flash 别名(0x00000000, 由 BOOT 脚决定)  │
             │   主 Flash 0x08000000 (程序+常量)              │
             │   系统 bootloader 0x1FFF0000 (ST 串口烧录固件)  │
             │   H7 的 ITCM 0x00000000 (指令紧耦合内存)        │
 0x2000_0000 ├──────────────────────────────────────────────┤
             │ SRAM 区: F4 主 SRAM 128K / H7 的 DTCM 128K     │
             │   F4 的 CCM 在 0x10000000 (SRAM 区之下)        │
             │   H7 的 AXI SRAM 0x24000000 / D2 SRAM 0x30000000│
 0x4000_0000 ├──────────────────────────────────────────────┤
             │ 外设区: 全部外设寄存器 (GPIO/UART/SPI/CAN...)   │
             │   F4 备份 SRAM 0x40024000 (VBAT 供电, 4K)      │
 0x6000_0000 ├──────────────────────────────────────────────┤
             │ 外部存储区: FSMC/FMC 外扩; H7 QSPI 内存映射      │
 0xE000_0000 ├──────────────────────────────────────────────┤
             │ 系统区: NVIC / SCB / SysTick / 调试组件         │
 0xFFFF_FFFF └──────────────────────────────────────────────┘

三个直接可用的推论：其一，解引用空指针在 PC 上必崩，在 MCU 上读到的是 0x00000000 处的 Flash 别名（向量表前几项）——读不报错、写才 HardFault，所以「空指针读没崩」不等于没踩空；其二，给野指针赋值时，落在 0x40000000 段就是改外设寄存器，落在 SRAM 段就是改别人的变量，两种都是「写坏了不知道谁」的典型来源；其三，函数指针指向非代码区，取指失败触发 HardFault（INVSTATE，10.1 节）。

9.2 段与启动流程：变量是怎么被放进内存的

编译器把代码和数据按段（Section）组织，链接器把各段装进地址空间。七个标准段的内容与去向：

段 内容 最终位置
.isr_vector 中断向量表（复位入口 + 各中断函数地址） Flash 最开头
.text 函数代码 Flash
.rodata const 常量、字符串字面量 Flash
.data 有初值的全局/静态变量（int x = 5;） 运行时在 RAM；初值存 Flash，启动时拷过去
.bss 无初值/零初值的全局/静态变量（int y;） RAM，启动时清零（不占 Flash）
.heap malloc 的堆 RAM（启动文件里定大小）
.stack 调用栈 RAM 顶端，向下生长

「启动时拷 .data、清 .bss」正是复位后 main 之前发生的事，读懂它就懂了「为什么全局变量不用初始化也有确定的值」：

/* startup_stm32f407xx.s 的等价伪代码 */
uint32_t *src = &_sidata;                    /* .data 的 Flash 初值存放起点 */
uint32_t *dst = &_sdata;                     /* .data 在 RAM 的起点(0x20000000) */
while (dst < &_edata)  *dst++ = *src++;      /* ① 把有初值变量的初值从 Flash 拷进 RAM */
for (dst = &_sbss; dst < &_ebss; dst++) *dst = 0;   /* ② .bss 整段清零 */
main();

9.3 STM32 内存地图：F407 与 H743

同是「1MB 级 RAM」的芯片，区域划分完全不同，每个区域「谁能访问、多快、放什么」才是选区依据（此表与 8.2 节 DMA 可达性矩阵配合使用）：

STM32F407VGT6（1 MB Flash + 192 KB RAM）
区域 地址 容量 谁能访问 定位与用途
主 SRAM 0x20000000 128 K CPU + DMA + 全部总线主设备 默认的家：全局变量、栈、堆、全部 DMA 缓冲
CCM（内核耦合 RAM） 0x10000000 64 K 仅 CPU（D-Bus 专线） DMA 不可达、不能执行代码；放 CPU 密集数据：控制律状态、滤波缓冲、printf 临时区。快且无总线争抢
备份 SRAM 0x40024000 4 K CPU（VBAT 纽扣电池供电） 主电源断电后内容保持：标定参数、故障黑匣子
主 Flash 0x08000000 1 M CPU 取指 + 只读 代码 + 常量；擦写有寿命（1.2 节），掉电保持
STM32H743（2 MB Flash + 约 1 MB RAM，多域架构）
区域 地址 容量 谁能访问 定位与用途
ITCM 0x00000000 64 K 仅 CPU 取指 关键函数/ISR 就地全速执行，零等待零争抢
DTCM 0x20000000 128 K CPU + MDMA（D2 的 DMA1/2 不可达） 数据全速区（480 MHz 零等待），实时控制数据首选；不经过缓存，无一致性问题
AXI SRAM（D1） 0x24000000 512 K 全部主设备（经 Cache） 默认大数组去所；带 D-Cache，DMA 缓冲要处理一致性（8.5 节）
D2 SRAM1/2/3 0x30000000 128+128+32 K D2 域主设备（DMA1/2、以太网、USB HS） 外设 DMA 缓冲主战场（8.2 节矩阵中全绿）
D3 SRAM4 0x38000000 64 K D3 域（DMA3/4、MDMA） 常被整块配成非缓存区专职放 DMA 缓冲（8.5 节解法二）
备份 SRAM 0x38800000 4 K VBAT 同 F4

F4 与 H7 最容易踩的同名不同义陷阱：0x20000000 这个地址在 F407 是「DMA 友好的主 SRAM」，在 H743 是「DMA1/2 到不了的 DTCM」。沿用 F4 习惯在 H7 上定义 DMA 缓冲（不显式指定区域），缓冲落在 DTCM，DMA 静默失败——这是 F4 迁 H7 的第一大事故来源。

9.4 把变量与函数放到指定区域

「放到指定区域」由两步合作完成：编译期用 __attribute__((section("名字"))) 给变量/函数打段标签，链接期在链接脚本里给这个段指定落地地址。以「把高频访问的滤波状态放进 F407 的 CCM」为例：

/* ① C 侧: 打段标签 */
#define IN_CCMRAM __attribute__((section(".ccmram")))

IN_CCMRAM static float lpf_state[256];          /* 这个数组将被放进 CCM */

/* ② 链接脚本侧: STM32F407VGTx_FLASH.ld 增加内存区与段 (GCC/CubeIDE) */
MEMORY
{
  FLASH  (rx)  : ORIGIN = 0x08000000, LENGTH = 1024K
  RAM    (xrw) : ORIGIN = 0x20000000, LENGTH = 128K
  CCMRAM (xrw) : ORIGIN = 0x10000000, LENGTH = 64K     /* ← 新增内存区 */
}

/* 在 .bss 段之后追加: 收集所有 .ccmram 标签的对象 */
  .ccmram (NOLOAD) :
  {
    . = ALIGN(4);
    *(.ccmram)
    *(.ccmram*)
    . = ALIGN(4);
  } >CCMRAM

Keil（MDK）不用链接脚本，等价物是分散加载文件（Scatter File）：

; Keil scatter 文件: 新增一个执行域
LR_IROM1 0x08000000 0x00100000  {
  ER_IROM1 0x08000000 0x00100000  {
    *.o (RESET, +First)
    *(InRoot$$Sections)
    .ANY (+RO)
  }
  RW_IRAM1 0x20000000 0x00020000  { .ANY (+RW +ZI) }
  RW_CCMRAM 0x10000000 0x00010000  { *(.ccmram) }   ; ← 新增执行域
}

三个常用的「定点投放」配方：

/* 配方1: H7 把高频中断处理函数放 ITCM 全速执行
   (GCC 需配合链接脚本 .itcmram 段 AT>FLASH, 并在启动时从 Flash 拷入;
    Keil 的 scatter-load 自动完成拷贝) */
#define IN_ITCM __attribute__((section(".itcmram")))
IN_ITCM void imu_step_1khz(void) { /* 姿态环热点代码 */ }

/* 配方2: H7 把 DMA 缓冲定向到非缓存区/可达区 (8.2/8.5 节的落地手段) */
#define IN_DMA_BUF __attribute__((section(".dma_buffer"), aligned(32)))
IN_DMA_BUF static uint8_t can_rx_dma[256];
/* 链接脚本: .dma_buffer (NOLOAD) : { *(.dma_buffer) } >RAM_D2  (基地址 0x30000000) */

/* 配方3: 参数放备份 SRAM, 断电保持 (注意 NOLOAD 防启动清零!) */
#define IN_BKPSRAM __attribute__((section(".bkpsram")))
IN_BKPSRAM static struct {
    uint32_t magic;            /* 魔数 0xCAFEF00D: 首次上电识别"这是有效数据" */
    float    gyro_bias[3];    /* 陀螺零偏标定值 */
    uint32_t reboot_count;
} g_params;
/* 链接脚本: BKP (xrw) : ORIGIN = 0x40024000, LENGTH = 4K
              .bkpsram (NOLOAD) : { *(.bkpsram) } >BKP          */

void bkpsram_init(void)
{
    __HAL_RCC_PWR_CLK_ENABLE();
    HAL_PWR_EnableBkUpAccess();                       /* 解锁备份域写权限 */
    __HAL_RCC_BKPSRAM_CLK_ENABLE();
    PWR->CSR |= PWR_CSR_BRE;                          /* 开备份域稳压器 */
    while (!(PWR->CSR & PWR_CSR_BRR)) { }             /* 等就绪 */

    if (g_params.magic != 0xCAFEF00D) {              /* 首次上电/电池耗尽 */
        memset(&g_params, 0, sizeof g_params);
        g_params.magic = 0xCAFEF00D;
    }
}

把东西放对地方之后，验证手段是看 map 文件（链接器输出的分配清单）：搜索变量名即可看到它最终落在哪个地址，对照 9.3 节地图核对区域是否正确。map 文件还能看到每个 .o 文件贡献了多少 Flash/RAM——内存超限时的「减脂体检表」。

9.5 栈与堆

栈：大小靠测，不靠猜

栈存放局部变量、函数参数与中断现场，从 RAM 顶端向下生长；CubeMX 生成的启动文件默认给 1 KB（_Min_Stack_Size，Keil 版是 Stack_Size EQU 0x400）——对带 printf 和多层调用的真实程序明显不够。栈溢出的后果是「安静地踩坏紧挨着栈底的数据」：变量莫名被改、HardFault 地址随机。与其猜，不如测量：

/* 栈水位线法: 上电把整个栈填特征值, 运行后扫描从未被覆盖的部分 */
extern uint32_t _estack;      /* 栈顶(RAM 高地址端), 链接脚本提供 */
extern uint32_t _sstack;      /* 栈底(低地址端) */
#define STACK_CANARY 0xA5A5A5A5U

void stack_watermark_init(void)
{
    for (uint32_t *p = &_sstack; p < &_estack; p++) *p = STACK_CANARY;
}

uint32_t stack_used_peak(void)   /* 返回历史峰值用量(字节) */
{
    uint32_t *p = &_sstack;                       /* 栈向下生长: 未用区域靠近栈底 */
    while (p < &_estack && *p == STACK_CANARY) p++;
    return (uint32_t)((&_estack - p) * 4);
}
/* 用法: 跑遍全部功能路径(含最深中断嵌套)后读数, 配置 = 峰值 × 1.5 起步 */

上 RTOS 后每个任务有独立栈，用系统自带 API 查：uxTaskGetStackHighWaterMark(NULL) 返回剩余最小值（FreeRTOS）。两个配套纪律：递归与大型局部数组（char buf[1024] 写在函数里）是栈杀手，大缓冲一律上移为全局/静态或池分配；中断嵌套共享主栈（MSP），最坏嵌套深度要在水位测试中覆盖到。

堆：newlib 的 malloc 是怎么工作的

GCC 工具链的 malloc 由 newlib 库实现，它自己不认识内存布局，每次分配都通过 _sbrk()（system break，系统断点）这个「钩子」向系统要内存。MCU 上没有操作系统，这个钩子要自己实现（CubeIDE 已生成简版）：

/* newlib 的 malloc → _sbrk: 堆从 .bss 结束处向上长, 顶部留给栈 */
extern uint8_t _end;                 /* 链接脚本符号: .bss 结束 = 堆起点 */
extern uint8_t _estack;              /* 栈顶 */
static uint8_t *heap_ptr = &_end;

void *_sbrk(ptrdiff_t incr)
{
    uint8_t *prev = heap_ptr;
    if (heap_ptr + incr > (uint8_t *)&_estack - 512)   /* 预留512字节保命栈 */
        return (void *)-1;                              /* 返回-1 = ENOMEM */
    heap_ptr += incr;
    return prev;
}

注意堆大小不是固定预留的——它是「.bss 结束处到栈之间的全部空余」，Heap_Size 只影响某些工具链的静态预留。malloc 的真问题不在大小，在下面这一节。

9.6 内存碎片：为什么嵌入式慎用 malloc

malloc/free 是「任意大小、任意时机」的通用分配器，代价是空闲内存会被切成不连续的碎片：

 运行 3 天后的堆 (理想 vs 现实):
 期望: |███ 24K 空闲 ███|           现实: |A|1K空|B|2K空|C|1K空|D|...|1K空|
                                    总空闲 24K, 但最大连续块只有 2K
                                    → 此时申请一个 8K 缓冲: 失败!
 碎片三要素: ①分配时机随机  ②大小混杂  ③生命周期交错 (短命块插在长命块之间)
 同时满足时, 碎片随运行时间单调恶化 — 表现为"跑几天就崩, 重启就好"

嵌入式系统往往 7×24 运行且无交互手段，碎片是「慢性病」：测试几天测不出来，交付后按月发作。治理策略按彻底程度排序：

策略 做法 适用
① 全静态 所有内存在编译期确定：全局数组 + _Static_assert 核算尺寸 逻辑固定的控制类固件（大多数场景的最优解）
② 一次性分配 初始化阶段把整个运行期的内存全部分好，运行期只引用不申请 对象集合固定（N 路传感器、M 个缓冲）
③ 固定块内存池 池内所有块同尺寸，O(1) 分配释放，结构上不可能产生碎片 运行期确需动态申请的场景（报文对象、消息队列节点）
④ 分级池 按大小档位（如 16/64/256/1024 B）各建一个固定池，申请时按档分配 对象大小跨度大但档位可枚举
⑤ TLSF 等通用分配器 O(1) 的实时分配算法，碎片可控但不为零 确需任意大小动态分配的复杂中间件场景（FreeRTOS 的 heap_4 属于此类——首次适配 + 合并，实现见 9.7 节走读）

固定块内存池的原理极简单且优雅：把内存划成等大的块，空闲块的头部空间被复用来串成单向链表——分配就是摘链头，释放就是头插回去，两次操作都是 O(1) 且无查找、无合并，天然零碎片。完整实现（约 50 行，可直接入库）：

/* mempool.c —— 固定块内存池: O(1) 分配/释放, 结构性零碎片 */
typedef struct {
    uint32_t block_size;      /* 每块字节数(已对齐) */
    uint32_t free_count;      /* 剩余块数 */
    uint32_t total_count;     /* 总块数 */
    void     *free_head;      /* 空闲链表头 */
} mem_pool_t;

void pool_init(mem_pool_t *p, void *mem, uint32_t mem_size, uint32_t block_size)
{
    if (block_size < sizeof(void *)) block_size = sizeof(void *);
    block_size = (block_size + 3u) & ~3u;          /* 4 字节对齐 */

    p->block_size  = block_size;
    p->total_count = mem_size / block_size;
    p->free_count  = p->total_count;
    p->free_head   = mem;

    /* 把空闲块串成链: 第 i 块开头写入第 i+1 块地址 (mem 建议放 .bss, 天然清零) */
    uint8_t *cur = (uint8_t *)mem;
    for (uint32_t i = 0; i + 1 < p->total_count; i++) {
        void *next = cur + block_size;
        memcpy(cur, &next, sizeof(next));
        cur += block_size;
    }
}

void *pool_alloc(mem_pool_t *p)
{
    if (p->free_count == 0) return NULL;            /* 池满: 显式失败, 调用方必须处理 */
    void *blk = p->free_head;
    memcpy(&p->free_head, blk, sizeof(void *));     /* 摘链头 */
    p->free_count--;
    return blk;
}

void pool_free(mem_pool_t *p, void *blk)
{
    if (blk == NULL) return;
    memcpy(blk, &p->free_head, sizeof(void *));     /* 头插回空闲链 */
    p->free_head = blk;
    p->free_count++;
}

使用示例与工程纪律：

/* 例: CAN 报文对象池 —— 中断收包 → 队列 → 任务消费 的标准配套 */
static mem_pool_t g_msg_pool;
static uint8_t    g_msg_mem[64 * sizeof(msg_t)];   /* 64 块, 放 DMA 可达区 */

void app_init(void) { pool_init(&g_msg_pool, g_msg_mem, sizeof g_msg_mem, sizeof(msg_t)); }

/* 中断里分配(生产者): */
msg_t *m = pool_alloc(&g_msg_pool);
if (m) { m->id = rx.StdId; queue_push(&q, m); }
/* 池满返回 NULL: 必须显式丢弃并计数, 绝不阻塞中断 */

/* 任务里释放(消费者): */
pool_free(&g_msg_pool, m);
纪律 原因
中断中分配/释放需短暂关中断或用 RTOS 临界区包裹 链表头指针被主循环与中断同时修改会损坏链；固定块操作只需几条指令，关中断代价可忽略
池大小按「峰值同时在用对象数」× 1.5 配置 池满是明确故障（计数器可见），比碎片崩溃可诊断得多
块内对象必须先清零再使用（或约定池初始化清零） 复用块带着上一任对象的数据，是信息泄漏与逻辑串台的经典来源
杜绝「同一内存既进池又 free」 双重释放把同一块插两次链，链上出现自环，后续分配拿到重叠内存

9.7 进阶：FreeRTOS heap_4 源码走读

9.6 节的固定池解决了「等大对象」的分配，但确实需要「任意大小」的运行期分配时，工程界的标准答案是 FreeRTOS 的堆实现。FreeRTOS 内核（FreeRTOS-Kernel/portable/MemMang/）提供五种可选堆，新工程默认选 heap_4，全部约 300 行——规模恰好适合逐行读懂，也是理解一切通用分配器（dlmalloc、TLSF）设计取舍的最小标本。本节基于部署最广的 v10.4.x 源码走读（新版本有细节重构，以随工程分发的内核源码为准，核心算法不变）。

9.7.1 五种堆实现一览：heap_4 为什么是默认

实现 能 free 吗 空闲块合并 算法 适用与短板
heap_1 不能 — 只分配：指针推进即分配 对象集合固定的简单系统；完全确定、零开销，但内存一次性消耗
heap_2 能 无 空闲链按大小排序，最佳适配 历史版本；反复分配/不同大小场景碎片单调恶化，已被 heap_4 取代
heap_3 能 无 给 stdlib 的 malloc/free 套调度锁 必须用 C 库生态时；大小受制于链接器堆，编译期不可预算
heap_4 能 双向合并 空闲链按地址排序，首次适配 + 切割 + 相邻合并 默认推荐：合并机制把相邻碎片拼回去，碎片可控；查找最坏 O(n)
heap_5 能 双向合并 heap_4 + 多段不连续内存 H7 多 RAM 域 / 外挂 SRAM 场景（9.7.8 节）

heap_2 与 heap_4 的一字之差正是整个设计的题眼：空闲链按「大小」排序就无法廉价地做相邻合并（邻居在地址上不相邻），按「地址」排序则合并只需一次地址加法比对——heap_4 用「首次适配」换来了「O(1) 合并判定」，这是通用分配器里最常见的权衡之一。

9.7.2 数据结构：块头 BlockLink_t 与三件静态家当

heap_4 的全部状态只有三件家当：堆地皮 ucHeap、空闲链表头 xStart、尾哨兵 pxEnd。每个块（无论空闲还是已分配）前面贴一个 8 字节块头：

typedef struct A_BLOCK_LINK {
    struct A_BLOCK_LINK *pxNextFreeBlock;  /* 链表下一个节点(仅空闲块有效) */
    size_t xBlockSize;                     /* 本块总大小(含这 8 字节头); bit31 = 已分配旗标 */
} BlockLink_t;                             /* 32 位机 sizeof = 8 字节, 按 8 对齐 */

static uint8_t ucHeap[ configTOTAL_HEAP_SIZE ];   /* 堆地皮: .bss 里的一块静态数组 */
static BlockLink_t xStart;                        /* 空闲链表头(数组外, 不占堆) */
static BlockLink_t *pxEnd = NULL;                 /* 尾哨兵; NULL 同时充当"未初始化"标志 */

static size_t xFreeBytesRemaining;                /* 当前剩余字节 */
static size_t xMinimumEverFreeBytesRemaining;     /* 历史最低水位 → 配置堆大小的依据 */
static size_t xNumberOfSuccessfulAllocations;     /* 统计: 成功分配次数 */
static size_t xNumberOfSuccessfulFrees;           /* 统计: 成功释放次数 */

#define heapMINIMUM_BLOCK_SIZE  ( xHeapStructSize << 1 )  /* 16B = 2×头: 能独立存在的最小块 */
/* xBlockAllocatedBit = 1 << 31: xBlockSize 最高位当"已分配"旗标, 不计入大小 */

四个关键约定，后面每个函数都在用它们：其一，块头内联在块前面——由返回给用户的指针回退 8 字节即得块头（vPortFree 的入口动作）；其二，xBlockSize 永远是 8 的倍数，最高位（bit31）挪用作「已分配」旗标，空闲块此位为 0；其三，只有空闲块会挂在链上且 next 有效，已分配块的 next 恒为 NULL——这是双重释放检测的依据；其四，heapMINIMUM_BLOCK_SIZE = 16：任何块最小 16 字节（头 8 + 至少 8 的载荷），分配 1 字节实际也吃掉 16 字节。

9.7.3 prvHeapInit：堆的初始布局

初始化只做一件事：把整个堆摆成「一块大空闲块 + 尾哨兵」。注意 xStart 和 pxEnd 的块头都不在 ucHeap 之外白占地方——xStart 是外部静态变量，pxEnd 的 8 字节头放在堆的最末尾（这正是初始可用空间是 configTOTAL_HEAP_SIZE − 8 的原因）：

 以 configTOTAL_HEAP_SIZE = 1024 为例 (8 字节对齐, 头 8 字节):

 字节:  0         8                                    1016    1024
       ┌─────────┬────────────────────────────────────────┬────────┐
       │ 头: 1016 │           空闲载荷区 1008 B             │ 头: 0  │
       │ 空闲块   │                                        │ pxEnd  │
       └─────────┴────────────────────────────────────────┴────────┘
            ▲                                                ▲
   xStart.pxNextFreeBlock ────► 这块 1016B ────► pxEnd.pxNextFreeBlock = NULL

 初始: xFreeBytesRemaining = 1016 (= 1024 − pxEnd 的 8 字节)

初始化在第一次调用 pvPortMalloc 时惰性触发（pxEnd == NULL 即未初始化），prvHeapInit 本身只是三步：对齐地皮起点 → 摆 pxEnd → 把起点到 pxEnd 之间声明成一整块空闲块挂上链。

9.7.4 pvPortMalloc：首次适配 + 块切割

分配的主干是「沿链找第一个够大的块，切下需要的部分，剩余留回链上」。逐段读（节选有删改，保留全部主干逻辑）：

void *pvPortMalloc( size_t xWantedSize )
{
    BlockLink_t *pxBlock, *pxPreviousBlock, *pxNewBlockLink;
    void *pvReturn = NULL;

    vTaskSuspendAll();                     /* ① 调度锁(挂起任务切换)而非关中断, 见 9.7.8 */
    {
        if( pxEnd == NULL )
            prvHeapInit();                 /* ② 惰性初始化 */

        if( ( xWantedSize & xBlockAllocatedBit ) == 0 )   /* ③ 请求大到碰 bit31 → 直接失败 */
        {
            xWantedSize += xHeapStructSize;               /* ④ 头部计入: 真实需求 = 想要的 + 8 */
            if( ( xWantedSize & portBYTE_ALIGNMENT_MASK ) != 0 )   /* ⑤ 向 8 对齐 */
                xWantedSize += portBYTE_ALIGNMENT -
                               ( xWantedSize & portBYTE_ALIGNMENT_MASK );

            /* ⑥ 首次适配: 沿地址序链表找第一个 xBlockSize ≥ 请求 的空闲块。
                  注意退出条件: pxEnd 的 pxNextFreeBlock == NULL 兼作链尾判据 */
            pxPreviousBlock = &xStart;
            pxBlock = xStart.pxNextFreeBlock;
            while( ( pxBlock->pxNextFreeBlock != NULL ) &&
                   ( pxBlock->xBlockSize < xWantedSize ) )
            {
                pxPreviousBlock = pxBlock;
                pxBlock = pxBlock->pxNextFreeBlock;
            }

            if( pxBlock != pxEnd )         /* ⑦ 撞到哨兵 = 全堆找不到能装下的块 */
            {
                pvReturn = ( void * )( ( uint8_t * )pxPreviousBlock->pxNextFreeBlock
                                       + xHeapStructSize );   /* 载荷 = 块地址 + 8 */

                /* ⑧ 切割: 仅当剩余 > 16B(最小合法块)才切; 否则整块给出,
                     多出的部分留在已分配块里(内部碎片, 但链上不会出现非法小块) */
                if( ( pxBlock->xBlockSize - xWantedSize ) > heapMINIMUM_BLOCK_SIZE )
                {
                    pxNewBlockLink = ( void * )( ( uint8_t * )pxBlock + xWantedSize );
                    pxNewBlockLink->xBlockSize = pxBlock->xBlockSize - xWantedSize;
                    pxBlock->xBlockSize = xWantedSize;

                    /* 新空闲块插入链上(复用 vPortFree 的插入+合并函数) */
                    prvInsertBlockIntoFreeList( pxNewBlockLink );
                }

                xFreeBytesRemaining -= pxBlock->xBlockSize;
                xNumberOfSuccessfulAllocations++;
                if( xFreeBytesRemaining < xMinimumEverFreeBytesRemaining )
                    xMinimumEverFreeBytesRemaining = xFreeBytesRemaining;   /* 记水位 */

                pxBlock->xBlockSize |= xBlockAllocatedBit;   /* ⑨ 置已分配旗标 */
                pxBlock->pxNextFreeBlock = NULL;             /*    已分配块 next 恒 NULL */
            }
        }
    }
    ( void )xTaskResumeAll();

    #if( configUSE_MALLOC_FAILED_HOOK == 1 )
    if( pvReturn == NULL )
        vApplicationMallocFailedHook();     /* ⑩ 失败钩子: 记录/降级, 由工程实现 */
    #endif

    return pvReturn;                        /* 失败时调用方拿到 NULL, 必须检查 */
}

这段代码的性价比账目值得算一遍，理解「每一笔分配的真实成本」：

调用 请求 +8 头 8 对齐后 实际吃掉 载荷利用率
分配 1 字节 1 9 16 16 B（最小块） 6%
分配 200 字节 200 208 208 208 B 96%
分配 100 字节 100 108 112 112 B 89%

结论直接可用：小块分配的固定成本是 8–16 字节——这也是 9.6 节固定池在每个块里白送 4 字节链表指针的对照面：池把管理开销摊到整池，heap_4 把开销摊到每块。频繁分配小对象时，池的内存效率显著更高。

9.7.5 vPortFree：完整性校验 + 双向合并

释放分两层：外层 vPortFree 做完整性与并发控制，内层 prvInsertBlockIntoFreeList 做插入与合并——后者是 heap_4 区别于 heap_2 的全部价值所在。

void vPortFree( void *pv )
{
    uint8_t *puc = ( uint8_t * )pv;
    BlockLink_t *pxLink;

    if( pv != NULL )                        /* free(NULL) 合法且为空操作 */
    {
        puc -= xHeapStructSize;             /* 回退 8 字节: 由载荷指针找回块头 */
        pxLink = ( void * )puc;

        /* 两道完整性校验, 拦截两类经典错误:
           ① 已分配位必须为 1  → 拦"重复释放"(第一次 free 已清位, 再 free 必触发断言)
           ② next 必须为 NULL  → 拦"释放从未分配过/越界写坏的地址"(只有空闲块才有 next)
           (依赖 configASSERT 生效; 断言没定义则两道防线都不存在!) */
        configASSERT( ( pxLink->xBlockSize & xBlockAllocatedBit ) != 0 );
        configASSERT( pxLink->pxNextFreeBlock == NULL );

        if( ( pxLink->xBlockSize & xBlockAllocatedBit ) != 0 )
        {
            if( pxLink->pxNextFreeBlock == NULL )
            {
                pxLink->xBlockSize &= ~xBlockAllocatedBit;   /* 摘旗: 变回空闲块 */

                vTaskSuspendAll();
                {
                    prvInsertBlockIntoFreeList( pxLink );    /* 核心: 插入+合并, 见下 */
                    xFreeBytesRemaining += pxLink->xBlockSize;
                    xNumberOfSuccessfulFrees++;
                }
                ( void )xTaskResumeAll();
            }
        }
    }
}

static void prvInsertBlockIntoFreeList( BlockLink_t *pxBlockToInsert )
{
    BlockLink_t *pxIterator;
    uint8_t *puc;

    /* ① 按地址升序找插入点: 挂在"最后一个地址低于目标块"的节点后面。
          纯遍历, 链越长越慢 —— free 的最坏 O(n) 就在这层循环 */
    for( pxIterator = &xStart;
         pxIterator->pxNextFreeBlock < pxBlockToInsert;
         pxIterator = pxIterator->pxNextFreeBlock )
    {
        /* 循环体为空: 只为推进指针 (哨兵 pxEnd 地址必高于一切块, 循环必然终止) */
    }

    /* ② 后邻合并: 目标块尾部恰好贴着下一个空闲块的头 → 吞并它 (两块并一块) */
    puc = ( uint8_t * )pxBlockToInsert;
    if( puc + pxBlockToInsert->xBlockSize ==
        ( uint8_t * )pxIterator->pxNextFreeBlock )
    {
        pxBlockToInsert->xBlockSize += pxIterator->pxNextFreeBlock->xBlockSize;
        pxBlockToInsert->pxNextFreeBlock =
            pxIterator->pxNextFreeBlock->pxNextFreeBlock;
    }
    else
    {
        pxBlockToInsert->pxNextFreeBlock = pxIterator->pxNextFreeBlock;
    }

    /* ③ 前邻合并: 前一个空闲块的尾部恰好贴着目标块的头 → 让它吞并目标块
          (此时目标块头整个消失, 被前邻的块尾覆盖) */
    puc = ( uint8_t * )pxIterator;
    if( puc + pxIterator->xBlockSize == ( uint8_t * )pxBlockToInsert )
    {
        pxIterator->xBlockSize += pxBlockToInsert->xBlockSize;
        pxIterator->pxNextFreeBlock = pxBlockToInsert->pxNextFreeBlock;
    }
    else
    {
        pxIterator->pxNextFreeBlock = pxBlockToInsert;
    }
}

「地址相邻」的判定就一行加法：前块地址 + 前块大小 == 后块地址——这正是 9.7.1 节说「按地址排序才有廉价合并」的兑现处。两个方向的合并组合出四种释放情形：只挂链（前后都不相邻）、只吞后邻、只被前邻吞、三块并一块（前邻吞并目标 + 目标已吞后邻）。

9.7.6 完整演算：1 KB 堆上的一轮分配与释放

把上面的逻辑在纸上跑一遍，是确认读懂了的唯一标准。初始布局见 9.7.3（总 1016 可用），序列如下：

 初始:
 xStart ──► [ 空 1016 |@0] ──► pxEnd                            剩余 1016

 ① pvPortMalloc(200):  200+8=208, 首块即满足, 切割 →
 xStart ──► [A 用 208|@0] ──► [ 空 808|@208] ──► pxEnd          剩余 808

 ② pvPortMalloc(100):  100+8=108→对齐112, 首块(808)满足, 切割 →
 xStart ──► [A 用 208] ──► [B 用 112|@208] ──► [ 空 696|@320] ──► pxEnd
                                                                剩余 696

 ③ vPortFree(A): A@0 插入。后邻: 0+208=208 ≠ 320, 不相邻;
                前邻: 前一个是 xStart(在堆外), 不相邻 → 仅挂链
 xStart ──► [A 空 208] ──► [B 用 112] ──► [ 空 696|@320] ──► pxEnd
                                                                剩余 904

 ④ vPortFree(B): B@208 插入, 双向合并 →
    后邻: 208+112 = 320 == 空696 的头 ✓ → 吞并 → B 变成 808
    前邻: 0+208 = 208 == B 的头 ✓ → A 吞并 B  → A 变成 1016
 xStart ──► [ 空 1016|@0] ──► pxEnd                            剩余 1016 ✓ 完全复原

第 ④ 步就是 heap_4 的灵魂时刻：两个 208 和 112 的碎片经一次 free 拼回整块 1016——同样的序列在 heap_2（无合并）下会留下永远取不回的空洞。这也是「生命周期交错的对象用 heap_4 基本安全，用 heap_2 会慢性失血」的机制解释。

9.7.7 设计权衡总结

设计点 heap_4 的选择 收益 / 代价
空闲链排序键 按块地址升序（非大小） 合并只需一次地址加法比对 / 分配查找无法按大小剪枝，最坏 O(n)
适配策略 首次适配（第一个够大的块） 实现最简、链前端小块可复用 / 低地址端易沉淀小碎片（靠合并补救）
管理头 内联在每块前面（8 B） 载荷→块头 O(1) / 每块固定开销；越界写坏邻居的头 = 下一次 free 时崩溃（本案发现场离案发地 8 字节）
并发控制 挂起调度器（非关中断） 临界区内中断照常响应，中断延迟不受影响 / ISR 内禁止调用（9.7.8）
损坏与误用检测 bit31 旗标 + next==NULL 双校验（configASSERT） 双重释放/野 free 可当场抓 / 断言未定义时防线消失；无越界写检测
碎片治理 只合并、不搬移 合并零成本 / 无法把不相邻的空闲块拼成大块（搬移需句柄间接层，MCU 上少用）

9.7.8 使用纪律与配套设施

  1. 中断服务函数里禁用 pvPortMalloc/vPortFree：临界区是「挂起调度器」——它防任务并发，不管中断并发；ISR 中调用会绕过锁破坏空闲链。中断收包要内存，用 9.6 节固定池（或者预分配）。
  2. 全工程只认一个分配器：ucHeap 是自包含的静态数组，不走 9.5 节的 _sbrk/链接器堆；newlib 的 malloc（printf 内部可能用到）与 heap_4 是两个互不知情的池，内存预算必须分开算、混用必然超卖。应用代码统一 pvPortMalloc/vPortFree。
  3. 用水位定大小，用遥测看碎片：
/* 配置依据: 跑遍全部业务后读历史最低水位 */
configTOTAL_HEAP_SIZE = xPortGetMinimumEverFreeHeapSize() 峰值 × 1.5;

/* 周期遥测: 除总量外, "最大空闲块"是碎片程度的直接指标
   (剩余 20KB 但最大块仅 2KB = 碎片已重, 大块申请将失败) */
HeapStats_t s;
vPortGetHeapStats( &s );
/* s.xAvailableHeapSpaceInBytes            当前剩余 */
/* s.xSizeOfLargestFreeBlockInBytes        最大空闲块 ← 碎片指标 */
/* s.xNumberOfFreeBlocks                   空闲块个数 ← 越多越碎 */
/* s.xMinimumEverFreeBytesRemaining        历史最低水位 */
/* s.xNumberOfSuccessfulAllocations/Frees  分配/释放次数 */
  1. 失败路径必须落地：configASSERT 与 vApplicationMallocFailedHook() 都要真实实现（记录 + 降级 + 复位），断言缺失时双重释放检测形同虚设。
  2. 热点路径不 malloc：分配/释放最坏 O(n) 且全程持调度锁——1 kHz 控制环内调用，抖动不可控。初始化期一次性分配或用池，运行期只引用。
  3. 想把堆搬到指定区域（如 H7 上放到 DMA 可达的 D2 SRAM）：启用 configAPPLICATION_ALLOCATED_HEAP=1，自己声明数组并打 section 标签，方法与 9.4 节完全相同：
#define configAPPLICATION_ALLOCATED_HEAP 1        /* FreeRTOSConfig.h */

/* 用户文件里自行定义地皮, 用 9.4 节的 section 手段定向: */
uint8_t ucHeap[ configTOTAL_HEAP_SIZE ] __attribute__((section(".dma_safe_ram")));
  1. 多段不连续内存用 heap_5：H7 想把「AXI SRAM + D2 SRAM」编成一个堆（9.3 节地图的现实应用），换 heap_5 并在调度器启动前声明区域表：
#include "FreeRTOS.h"
#include "task.h"

const HeapRegion_t xHeapRegions[] = {
    { ( uint8_t * ) 0x24000000UL, 512 * 1024 },   /* D1 域 AXI SRAM */
    { ( uint8_t * ) 0x30000000UL, 128 * 1024 },   /* D2 域 SRAM1 */
    { NULL, 0 }                                    /* 区域表必须以空项结尾 */
};
/* 调度器启动前调用, 之后 pvPortMalloc 语义与 heap_4 完全一致:
   从前往后用满一段才用下一段(分配就近), 合并只在段内进行 */
vPortDefineHeapRegions( xHeapRegions );

9.8 内存实践清单

  1. DMA 缓冲三查：地址在 DMA 可达区（8.2 矩阵）→ 首地址 aligned(32) → 长度 32 取整（M7）。
  2. 全局数组用 _Static_assert 做编译期核算：_Static_assert(sizeof(g_msg_mem) >= 64*sizeof(msg_t), "pool too small"); 把「运行期才发现池太小」提前到编译失败。
  3. 栈配置 = 实测峰值 × 1.5（9.5 节水位法），并在遥测里暴露「栈峰值」与「堆/池余量」两个运行时指标。
  4. 分配器选型口诀：能静态则静态 → 对象集合固定用一次性分配 → 运行期动态用固定池 → 万不得已才 malloc，且只在初始化期用。
  5. 上 FreeRTOS 后的三条铁律：动态申请统一 pvPortMalloc/vPortFree（9.7 节）；configTOTAL_HEAP_SIZE = xPortGetMinimumEverFreeHeapSize() 实测水位 × 1.5；中断内禁用任何堆操作，收包用池。
  6. 每次内存相关改动后看一眼 map 文件：新增最大对象是谁、各段涨了多少、有没有变量意外落进错误区域。

10. 调试与实战：从 HardFault 到稳定交付

嵌入式调试的难点在于现象与根因在时间与空间上都是错位的：今天写坏的指针，明天早上三点的死机才暴露。本章给出四类武器：HardFault 的现场取证方法（10.1）与三个完整案例（10.2，把「随机死机」变成「指名道姓」）、全局症状速查表（10.3，从现象反查章节）、调试工具选型与文档地图（10.4 / 10.5）。

10.1 HardFault 取证三步法

HardFault 是 Cortex-M 内核检测到非法操作后的强制跳转，默认的弱定义处理函数是个死循环——所以「程序莫名卡死」有一大半其实是进了 HardFault。取证三步：第一步区分是不是 HardFault（在处理函数里放一个明显的断点或 LED 翻转）；第二步提取现场（出错时的 PC 指针与错误状态寄存器）；第三步解码归因（查下表）。

/* fault.c —— HardFault 现场提取 (裸机通用) */

/* naked: 不生成函数序言, 保证能拿到"刚发生异常"时的原始栈指针 */
#if defined(__GNUC__)
__attribute__((naked)) void HardFault_Handler(void)
{
    __asm volatile(
        " tst lr, #4     \n"   /* EXC_RETURN 位2: 出异常前用的是主栈还是任务栈 */
        " ite eq         \n"
        " mrseq r0, msp  \n"   /* 主栈 MSP */
        " mrsne r0, psp  \n"   /* 任务栈 PSP (RTOS 场景) */
        " b HardFault_HandlerC "
    );
}
#endif

void HardFault_HandlerC(uint32_t *sp)
{
    /* 异常自动入栈的 8 个字: R0 R1 R2 R3 R12 LR PC xPSR */
    uint32_t pc   = sp[6];          /* 出错时正要执行的指令地址 ← 头号线索 */
    uint32_t lr   = sp[5];          /* 出错函数被谁调用 */
    uint32_t cfsr = SCB->CFSR;      /* 错误状态寄存器(组合): 告诉你"怎么错的" */
    uint32_t bfar = SCB->BFAR;      /* 总线出错的目标地址(当 BFARVALID 有效时) */

    /* 把四个值存进黑匣子(备份SRAM)或从 SWO 吐出, 然后: 复位或挂住待调试器 */
    fault_log_save(pc, lr, cfsr, bfar);
    while (1) { }
}
/* 拿到 PC 后: 在 map 文件里查"哪个函数包含这个地址", 即锁定案发函数 */

第三步解码 CFSR。它是三段组合（内存管理 + 总线 + 用法错误），最常用的位域与归因：

CFSR 位域 名称 含义 最常见根因
UFSR.16 UNDEFINSTR 取到无法识别的指令 数据被当代码执行（野函数指针、数组越界覆写代码区旁变量）
UFSR.17 INVSTATE 无效状态（跳转目标 Thumb 位不对） 函数指针赋值把整数当地址、中断向量表被改坏
UFSR.19 NOCP 执行浮点指令但 FPU 未使能 手写工程忘了 SCB->CPACR 使能 FPU（CubeMX 工程已自动处理）
UFSR.24 UNALIGNED 非对齐访问（且使能了非对齐陷阱） 把报文字节缓冲强转成 uint32_t * 直接解引用——先 memcpy 到对齐变量
BFSR.7 BFARVALID BFAR 里的地址有效 配合 SCB->BFAR 直接得到「访问了哪个非法地址」
BFSR.1/2 PRECISERR / IMPRECISERR 数据总线错误（精确/非精确） 访问未实现的地址空洞；非精确错误发生在写缓冲，地址不可查，更靠 PC 上下文推断
BFSR.3/4 UNSTKERR / STKERR 异常入栈/出栈失败 栈指针已坏 = 栈溢出的教科书症状，回 9.5 节做水位测量

配套一个微秒级计时工具（取证与性能测量两用）——DWT 周期计数器，随内核时钟逐周期计数：

/* DWT 周期计数器: 168MHz 下分辨率约 6ns, 32 位约 25.6 秒回绕 */

{
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;   /* 打开调试跟踪 */

10.2 HardFault 完整案例三则

取证方法只有配上真实现场才算掌握。本节给三个由浅入深的完整案例：案例 A 是旗舰案例，走完「寄存器 → CFSR 解码 → map 文件 → ASCII 侦探 → 反汇编 → 源码」的完整取证链；案例 B 演示 BFAR（总线错误地址寄存器）直指案发地址的「两分钟破案」；案例 C 演示栈溢出的特殊现场。三则故障模式均取自真实工程，可直接当作排练剧本——建议先遮住答案自己推一遍。

10.2.1 案例 A：报文长度字段未校验，栈被写穿

案情：无人机数传链路固件。台架单测一切正常，联飞约 10 分钟随机死机，复现概率约三成；死机时机与数传流量强相关——报文活跃时易炸。固件已内置 10.1 节的取证处理函数，死机后调试器 attach 读现场。

第一步：现场四件套。HardFault_HandlerC 存下的关键值，以及逐个解读：

 HardFault_HandlerC 捕获的现场:
 PC   = 0x41544144      ← 出错时正要执行的地址: 一个完全陌生的值
 LR   = 0x08004F5D      ← 合法的 Flash 地址 (0x08000000 段)
 CFSR = 0x00020000      ← 错误状态寄存器
 HFSR = 0x40000000      ← HardFault 状态寄存器
 BFAR = 0xE000ED38      ← 残留值, 不可信 (原因见下表)
寄存器 值 解读
CFSR 0x00020000 只有 UFSR.17（INVSTATE）置位 → 跳转目标的 Thumb 位为 0 →「跳转/返回到了非法地址」，不是访存出错
HFSR 0x40000000 FORCED 位：本质是 UsageFault，但工程没单独使能 UsageFault 向量，升级为 HardFault 进了取证函数（默认工程皆是如此）
BFAR 0xE000ED38 BFARVALID 未置位 → 此值是寄存器残留（恰好是 BFAR 寄存器自身的地址），无效。教训：BFARVALID=0 时 BFAR 一律不采信
PC 0x41544144 见第三步：它根本不是代码地址
LR 0x08004F5D 合法返回地址 → 调用链还活着，这是顺藤摸瓜的线索（第四步）

第二步：定性。INVSTATE + PC 是垃圾值 → 故障发生在「函数返回」这个动作上，不是函数体内执行出错。补充一个细节：0x41544144 的 bit0 = 0，POP {pc} 装载后把 T 位（Thumb 状态位）清零，取指前的状态检查直接失败 → INVSTATE；若垃圾值的 bit0 = 1，则会继续在非法地址取指，报成 IBUSERR（CFSR=0x00000100）。同一个 bug，死法随报文数据内容漂移——这就是「随机死机」面孔的来源之一。

第三步：PC 查 map 失败 → ASCII 侦探。

 在 map 文件里搜 0x41544144: 不属于任何函数/变量区间
   → 它不是代码地址, 是数据。

 四字节转 ASCII (小端): 0x44='D' 0x41='A' 0x54='T' 0x41='A' → "DATA"
   → 栈上的返回地址被报文内容覆盖了!

 结论: 某处发生栈缓冲越界写, 写穿了保存的返回地址。

第四步：LR 顺藤摸瓜。map 文件查 0x08004F5C（LR 去 Thumb 位），并反汇编该地址附近：

 map 文件节选:
   tele_parse_frame                      0x08004c80   0x80   tele_rx.o
   gps_rx_task                           0x08004e00   0x1a0  tele_rx.o
                                                    ↑ 0x08004f5c 落在 gps_rx_task 体内

 反汇编 0x08004f5c 附近:
 08004f58:  bl   0x08004c80  <tele_parse_frame>
 08004f5c:  mov  r1, r6              ← LR(0x08004f5d 去 Thumb 位)指回调用点下一条
                                        → 出错(返回时炸掉)的函数 = tele_parse_frame

第五步：回到源码。打开 tele_parse_frame，根因一行可见：

/* tele_rx.c —— 修复前: 长度字段来自报文本身, 未校验 */
void tele_parse_frame(const uint8_t *frame, uint16_t len)
{
    uint8_t payload[64];                     /* 栈上缓冲 */
    uint16_t payload_len = frame[1];         /* 长度字段是报文说的! */

    memcpy(payload, frame + 2, payload_len); /* 报文说 234, 就越界写 234 字节 */
    handle_payload(payload, payload_len);
}

 tele_parse_frame 的栈帧 (向下生长, 越界写从低地址往高地址涂):
   sp ──► ┌───────────────┐
          │ payload[64]   │ ← 合法写入区
          ├───────────────┤   本帧 payload_len = 0xEA(234) →
          │ 保存的 r4-r6  │ ← 越过 64 字节后开始遭殃
          │ 返回地址       │ ← 第 76~79 字节: 被 ASCII "DATA" 覆盖!
          ├───────────────┤
          │ 调用者栈帧…    │ ← 后续 150+ 字节继续涂, 更多变量被殃及
          └───────────────┘

第六步：修复。直接修复只加两行判断——但要把「长度字段不可信」立成规矩：

/* 修复: 一切来自报文的长度/索引字段都是不可信输入, 先验后用 */
void tele_parse_frame(const uint8_t *frame, uint16_t len)
{
    uint8_t payload[64];
    uint16_t payload_len;

    if (len < 2)
        return;                                   /* 帧头都不完整 */
    payload_len = frame[1];
    if (payload_len > sizeof(payload) || payload_len > (uint16_t)(len - 2))
        return;                                   /* 非法帧: 计数丢弃, 绝不 memcpy */

    memcpy(payload, frame + 2, payload_len);
    handle_payload(payload, payload_len);
}

系统性防御四条：

  1. 协议层：长度、索引、计数等来自线路的字段一律视为不可信输入——与测试台架同一个思路：把边界值（0 / 1 / 64 / 65 / 255）写进自动化回归，报文模糊测试常态化。
  2. 编译层：-fstack-protector-strong（栈保护金丝雀）或 MPU 栈区 guard，把「写穿后延迟爆炸」变成「当场报错」。
  3. 运行层：栈水位遥测（9.5 节）+ HardFault 黑匣子（CFSR/PC/LR 存进备份 SRAM，复位后上报）——下一次半分钟出结论。
  4. 流程层：本案修复后补一条「长帧」用例进回归集，防止下一个解析函数重蹈覆辙。

复盘：三成复现率怎么解释。越界写的 170 字节里，只有恰好压在返回地址上的那 4 字节决定死法（INVSTATE / IBUSERR / 还是根本不死机）；多数帧死得更安静——调用者的局部变量被涂改，表现为 GPS 数据莫名错乱而非死机。「现象与根因错位」不只是时间错位，还有形态错位：同一个 bug，今天死机、明天数据异常。

10.2.2 案例 B：BFAR 直指案发地址——两分钟破案

案情：数传固件偶发死机。现场：

 CFSR = 0x00008200   ← BFSR.PRECISERR(bit9) + BFARVALID(bit15)
 HFSR = 0x40000000
 BFAR = 0x20020000   ← 有效! 精确总线错误的案发地址
 PC   = 0x08005210   (合法 Flash 地址)
 LR   = 0x08004E36   (合法 Flash 地址)

解读只有两步。其一，PRECISERR + BFARVALID = 「数据访问出错，且出错地址已被捕获」→ BFAR 就是正在读写的那一个地址，不需要推理。其二，对照内存地图（9.1/9.3 节）：F407 的 SRAM 区是 0x20000000 起 128K，末字节 0x2001FFFF——0x20020000 恰好是 SRAM 结束之后的第一个不存在地址。结论：某个指针/下标一路扫过了整块 SRAM 的顶端。

/* 环形缓冲里找帧尾 0x0D —— 修复前 */
int find_frame_end(const uint8_t *buf)
{
    int i = 0;
    while (buf[i] != 0x0D)      /* 无边界: 缓冲里没有 0x0D 就一路扫出内存 */
        i++;
    return i;
}

/* 修复: 扫描循环必须带边界, 边界是协议给的(帧长), 不是数据给的(终止符) */
int find_frame_end(const uint8_t *buf, int max_len)
{
    int i = 0;
    while (i < max_len && buf[i] != 0x0D)
        i++;
    return (i < max_len) ? i : -1;   /* 没找到: 显式返回, 不假装成功 */
}

本案的「幸运」在于越界扫过了 SRAM 顶（必然撞上不存在的地址，当场炸）；若它在 SRAM 中段游荡，只会安静地读到别人的变量——BFAR 只在撞墙时才给真相，不能因为没有 fault 就认定没有越界。

案情：中断密集时段（数百 Hz 遥测 + 1 kHz 控制环）死机。现场：

 CFSR = 0x00001000   ← BFSR.STKERR(bit12): 异常"入栈"失败
 HFSR = 0x40000000

固件自遥测 无人值守期的自我暴露 栈水位、池余量、错误计数、最重任务耗时（DWT）——「跑几天才崩」类问题唯一的现场证据来源
