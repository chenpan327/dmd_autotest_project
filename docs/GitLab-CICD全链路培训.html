0. 全景图：一条 tag 触发的完整自动化链路

1. GitLab CI/CD 工作原理

1.1 核心概念与组件

概念是什么在本项目中的对应物
Pipeline（流水线）一次完整的自动化执行，由若干 stage 组成，同一 stage 内的 job 并行、stage 间串行每次 push / MR / 打 tag 都会生成一条，可在 GitLab 网页 CI/CD → Pipelines 看到全部历史
Stage（阶段）逻辑分组与顺序控制：前一个 stage 全部成功才进入下一个；任一 job 失败则整条流水线停在该 stagecode_check → build → release → notify 四段
Job（任务）最小执行单元，一段在 runner 上真实运行的 shell 脚本cppcheck-analysis / build_job / release_job / feishu_notify
Runner（执行器）
实际干活的机器上的代理进程，认领 job 并执行脚本dmd_cicd_runner_A，shell 执行器，宿主机 10.10.2.25（编译在 Docker 容器内进行）
Artifact（制品）job 运行中产生的文件，可上传回 GitLab 供下载或传递给后续 jobcppcheck 的 index.html 报告；release 的 ci_report/（30 天）
Variable（变量）注入 job 环境的键值对。来源：yml 内 variables:、GitLab 设置页（优先级更高）、流水线手动运行时手动填入NEXUS_URL、FEISHU_PLUGIN_ID 等；密钥类一律配在 GitLab 设置页并勾选 Masked
Rule（触发规则）决定"这个 job 在什么条件下要不要运行"的判断式见 1.4 节：同一个 yml 同时服务日常 push、MR 和 tag 三种场景

1.2 一次流水线的执行过程（原理）

  1. 事件触发：git push / 创建 MR / 推送 tag 到 GitLab，GitLab 按事件类型 + yml 的 rules 决定创建什么样的流水线、包含哪些 job；
  2. 调度派发：GitLab 服务端把待执行的 job 放入队列，注册在线的 runner 按标签（tags: dmd_cicd_runner_A）认领；
  3. 准备环境：runner 在宿主机准备好工作目录，按 yml 的 before_script → script → after_script 顺序执行 shell 命令（本项目 before_script 里做 Docker 环境检查，after_script 里清理编译容器）；
  4. 产物回收：job 成功后，yml 里 artifacts: 声明的文件被上传回 GitLab 存储，供网页下载或被 needs 声明的下游 job 拉取；
  5. 状态汇报：每个命令的退出码决定成败（非 0 即失败），配合 set -euo pipefail（任何一条命令失败立即终止）实现"fail-fast"，日志实时回传网页。

两个关键机制值得单独强调：

  • needs 依赖（DAG）：feishu_notify 声明了 needs: release_job，含义有二——必须等 release_job 成功才开始（发布失败绝不发通知），并自动下载它的 ci_report/ 产物。这把"发布成功"变成了通知的硬前提而非口头约定；
  • artifacts 传递：release_job 在编译现场生成 artifacts.tsv（每个制品的 conf / 文件名 / 下载链接 / MD5），notify 阶段直接读这份"清单"发评论、回填交付物——两个 stage 之间不靠约定的文件路径传话，靠 GitLab 的制品机制交接。

1.3 触发规则：一份 yml 服务三种场景

场景触发事件跑哪些 job目的
日常开发push 到任意分支（无 tag）cppcheck + build_job每次提交都被编译验证与静态扫描，问题在提交当场暴露
代码评审创建 / 更新 Merge Request同上合并前就能看到"这段代码能不能编译过、扫出什么问题"
正式发版推送 tagcppcheck + release_job + feishu_notify编译 → 归档 → 通知全自动

对应的 yml 片段（节选）——注意 cppcheck 对 C/C++ 文件变更才触发（纯文档提交不浪费算力），release 与 notify 只认 tag：

cppcheck-analysis:
  rules:
    - if: $CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_TAG == null
      changes: ["**/*.c", "**/*.cpp", "**/*.h", ...]   # 改了C/C++才扫
    - if: $CI_COMMIT_TAG                               # 发版必扫
release_job:
  rules:
    - if: $CI_COMMIT_TAG                               # 只有tag触发
feishu_notify:
  needs: [release_job]                                 # 发布成功才通知
  rules:
    - if: $CI_COMMIT_TAG

1.4 编译环境的隔离与复用

固件编译依赖 Zephyr/west 工具链，直接装在 runner 宿主机会污染环境。做法是每个 job 起一个一次性 Docker 容器（镜像 dmd_uav_env_image:v2，容器名含 job ID 天然防冲突），流程为：起容器 → 注入 SSH 私钥（拉 west 模块仓库用）→ west init/update 拉取 manifest 与依赖 → 对 strobe_light/config/ 下自动发现的全部 conf 逐个编译 → 校验每个 conf 都产出 .bin → docker cp 拷出产物 → 销毁容器。新增编译目标只需要往 config 目录加 conf 文件，不用改流水线。

2. 本项目流水线解剖：四个 stage 各自在做什么

2.1 stage1 — cppcheck 静态分析

  • 在 code_check:latest 容器内对仓库源码跑 cppcheck --enable=all，输出 XML 报告；
  • 用 Python 把 XML 转成可按严重级别筛选的 index.html，作为 artifact 保留 7 天，在 job 页面 Artifacts 处下载；
  • allow_failure: true：扫描发现问题不阻断流水线（当前定位为参考报告，后续可收紧为门禁）。

2.2 stage2 — build_job 构建验证（日常/MR）

  • 完整跑一遍与发版完全相同的编译流程，但不上传、不通知；
  • 价值：把"我本地能编过"升级为"在标准环境里能编过"，消灭"本地环境差异"这类最磨人的问题。

2.3 stage3 — release_job 发布（tag 触发）

与 build_job 相同的编译流程之外，多做四件事：

  1. 生成 MD5 校验文件：每个 .bin 配一个 xxx.bin_时间戳.md5，烧录前可校验完整性；
  2. 上传 Nexus：目标路径 http://10.10.2.25:8081/repository/strobe_light/<tag>/<时间戳>/<conf名>/，.bin 与 .md5 成对上传；
  3. 生成 ci_report 制品报告：artifacts.tsv（conf/文件名/下载链接/MD5值/MD5链接 五列清单）+ release_meta.env（tag、时间戳、流水线链接、触发人等），保留 30 天——这是下游一切"自动通知"的数据源；
  4. 任何一步失败（编译失败、产物缺失、上传失败）整条流水线红掉，不会产出半个版本。

2.4 stage4 — feishu_notify 回链通知（tag 触发）

这个 job 是"编译世界"与"研发管理世界"的桥梁，依次做五件事（全部只读 release_job 的 ci_report，不碰编译）：

  1. 解析工作项 ID：四个来源取并集——手动运行流水线时的变量 FEISHU_WORKITEM_IDS > tag 注释（正则 \b前缀-数字，带词边界防止 self-5 / conf-123 这类英文词误伤）> tag 所指 commit 的提交信息（把"关联工作项: …"写在 commit message 里同样生效）> 已合并 MR 的标题/描述（需配 GITLAB_API_TOKEN）；
  2. 非强制设计：四个来源都没写 ID 时，发布照常完成（编译 + 上传 Nexus），只是跳过飞书回链 / 流转 / 交付物回填，流水线不报错；
  3. 飞书鉴权：用插件的 plugin_id/secret 换取 plugin_token（token 约十分钟有效，每次现取）；
  4. 逐工作项发评论：调 OpenAPI 把制品清单（下载链接、MD5、流水线链接）评论到工作项的「评论/备注」；
  5. 交付物回填：把 版本信息 字段写为 tag、产物信息 字段写为 Nexus 页面链接（字段 key 按工作项类型在 FEISHU_DELIVERABLE_FIELDS 中配置）；
  6. 节点流转：对配置了动作的工作项自动 confirm 当前节点（推进工作流），必填的节点表单会自动用发布链接代填，避免被 400 卡住；
  7. （可选）群机器人卡片通知——GitLab 变量 FEISHU_BOT_WEBHOOK_URL 配上测试群机器人地址即启用，未配置自动跳过。

踩坑实录（维护者必读）：这条链路的每一环都"坏得很有性格"。已验证的失败模式与解法见第 3.6 节错误码表；两条最重要的经验——① 飞书 API 的工作项类型 key 是随机串（工作项 URL 里的 embed_dev 只是前端别名，API 不认，真实 key 要调 work_item/all-types 查）；② 新增的 feishu_post 调用必须显式带 X-PLUGIN-TOKEN / X-USER-KEY 鉴权头，漏了会收到 401 但 job 依然绿（降级设计会吞错），只能从「流转汇总」日志里发现。

3. 使用指南：日常开发、发版、通知测试与排障

3.1 日常开发：你只需要正常写代码

  1. 正常提交、正常 push——后台自动跑 cppcheck + 全量编译验证，编译不过当场红掉，Pipelines 页面点进失败 job 看日志；
  2. 提 MR 走评审——MR 流水线同样自动验证，评审者可以直接引用"流水线绿了"作为可合并依据；
  3. cppcheck 报告在对应流水线的 cppcheck-analysis job → Artifacts → index.html，浏览器打开可按严重级别筛选。

3.2 发版：两条命令，其余全自动

# 1) 打附注 tag（-a 必须带！注释里写工作项ID，需求m-/缺陷f-可写多个）
git tag -a test_0.1.1 -m "test_0.1.1 发布 需求:m-7153472781 缺陷:f-123"

# 2) 推送 tag —— 从这一秒起全自动
git push origin test_0.1.1

推送后无需任何操作，约十几分钟后以下内容全部就位：

环节在哪里看到内容
编译产物Nexus：10.10.2.25:8081 →Browse→ strobe_light → test_0.1.1 → 时间戳 → conf名strobe_light.bin + MD5 校验文件
工作项评论飞书工作项 → 评论/备注「[CI 自动回链]」：Tag、Commit、流水线链接、每个制品的下载地址与 MD5
交付物回填飞书工作项 → 交付物 → 交付版本信息 = tag 名；产物信息 = Nexus 页面链接（点击直达）
节点流转飞书工作项 → 节点详情当前节点自动 confirm，推进到下一节点
测试群通知飞书群（配置机器人后）卡片：版本、制品数、触发人、流水线与日志链接

3.3 tag 命名规范（前缀即用途声明）

前缀用途示例
debug_x.y.z研发自测版本debug_0.1.1
test_x.y.z发测试组验证test_0.1.1
dmd_x.y.z发生产 / 技术支持dmd_0.1.1

注释里的工作项 ID 前缀：需求 m-、缺陷 f-、项目 p-、嵌软开发 e-（大小写随意，可一次关联多个，逗号分隔）。ID 写在 tag 注释或 tag 所指 commit 的提交信息里均可；两处都不写时发布照常完成，只是不通知飞书（回链为非强制特性）。

3.4 失败重试：不用重新打 tag

评论 / 回填 / 流转环节失败时，编译与上传都是成功的，不需要重新打 tag。直接在对应流水线页面（CI/CD → Pipelines → 点进 tag 那条）对失败的 feishu_notify job 点 Retry——它会重新下载 ci_report、重新解析 tag 注释并重试飞书侧操作，几十秒出结果。修好 GitLab 设置页的变量后，同样用 Retry 验证。

3.5 通知测试群（一次性配置）

  1. 测试群里添加飞书自定义机器人，复制 Webhook 地址；
  2. GitLab → 项目 → Settings → CI/CD → Variables → 新增 FEISHU_BOT_WEBHOOK_URL（Masked）；
  3. 此后每次发版，群内自动收到卡片：版本号、制品数、触发人、流水线与日志直达链接。删掉该变量即停用，不影响其它环节。

3.6 排障速查：错误码 → 含义 → 处理

调试技巧：FEISHU_DRY_RUN=true（GitLab 变量）可让 notify 只打印请求不真发，用于验证 ID 解析与 payload 组装；日志里「节点流转汇总」「交付物回填汇总」两段是这两个环节的直接证据。

4. 为什么这么设计：稳定、可回溯与收敛

4.1 版本稳定可回溯：四个"锚点"串成证据链

"可回溯"的本质是：任何一次发布，都能沿一条完整的、无断点的引用链回答"谁、在什么时候、把哪次提交、编译成了什么、放在哪里、通知了谁"。这套链路用四个锚点把链焊死：

锚点机制回答的问题
tag = 版本身份附注 tag 指向确定的 commit，注释携带工作项 ID；tag 一旦推送不可变（重打即新版本）这个版本对应哪次代码？为了哪个需求？
commit SHA 全程携带评论、交付物、ci_report 里都写入完整 40 位 SHA产物与代码仓库如何互相对上？
Nexus 目录即存证tag/时间戳/conf 三级目录 + .md5 校验文件成对存在，只增不删这个版本的固件文件现在在哪？和当时上传的一致吗？
飞书工作项 = 过程账本评论（谁触发的、链接清单）+ 交付物字段 + 节点流转记录全部落库，ci_report 留档 30 天兜底这次发布通知了谁？测试依据什么验收？

对比手工流程的典型断链：本地编译的 bin 通过聊天窗口传输（无版本锚点、无 MD5、无归档）→ 测试出问题后"复现不了当时的状态"。自动化链路里不存在"环境不一致"和"文件对不上"这两类事故的生存空间——因为根本不存在手工环节。

4.2 收敛研发工作：一个入口，N 个出口

"无序发散"的根源是多入口：每个人按自己的习惯打包、按自己的路径传文件、按自己的措辞通知——信息格式不一、责任不清、遗漏难免。收敛的办法不是"要求大家细心"，而是把入口收窄到只有一个动作（打 tag），把其余全部变成机器行为：

环节手工方式本链路
编译各自电脑，环境各异标准容器内全 conf 编译，环境唯一
质量检查看心情每次提交自动 cppcheck + 编译验证
产物交付聊天窗口传文件，易丢失版本Nexus 按版本归档，链接永久有效
完整性校验无.md5 成对生成
通知测试群里@谁看运气群卡片自动推送（含全部链接）
需求/缺陷关联靠口头或事后补录tag 注释即关联，工作项自动评论
流程推进手工点节点，容易漏发布成功自动 confirm 推进
事后追溯翻聊天记录考古工作项一页看完全链路

同时注意这套机制收敛但不僵化的三处设计：日常 push 的验证是后台的，不打断写码节奏；cppcheck 当前是报告不是门禁，可以先推广意识再收紧标准；流转动作按前缀配置（FEISHU_WORK_ITEM_FLOW），哪些类型的工作项"发版即推进"是可以商量的策略，改一行配置即可调整。

4.3 对研发流程的三个正向约束

  1. 发布纪律前置：想在注释里写清需求 ID，就得先在飞书里立项建工作项——发布动作反过来倒逼"先有需求记录，再有版本产出"；
  2. 质量门槛前置：编译不过的提交立即暴露，"攒到发版才发现编不过"的雪崩场景消失；MR 流水线让"合并"有了客观依据；
  3. 测试验收有据：测试拿到的每个版本都自带 tag、MD5、工作项关联，提 bug 时引用 tag 即可精确定位，"你测的是哪个版本"永远不再是问题。

4.4 已知边界与演进方向

  • cppcheck 目前 allow_failure，建议运行一段时间后按基线收紧为门禁（新增 error 阻断合并）；
  • 产物信息链接当前取第一条制品，多 conf 多制品时可改为文本字段拼接清单；
  • 节点流转策略（哪些类型、推进到哪个节点）建议与项目管理流程对齐后固化到 yml 注释；
  • 所有飞书侧配置（字段 key、类型映射）集中在 yml variables 区，换空间/改模板只动一处。
